## 问题判断

用户指出的重复有源码依据，不是单纯的配色偏好。原规范要求“菜单是完整命令入口”，实现因而把桌面软件的菜单分类直接叠加在已有 Web 操作面上。

| 原实现 | 实际重复与影响 |
| --- | --- |
| 组态顶部：文件 / 编辑 / 视图 / 插入 / 排列 / 运行 | 撤销、复制、删除、组合、对齐、分布、网格、吸附已在工具栏；插入复刻左侧组件列表；运行复刻设计/预览 |
| 组件顶部：文件 / 编辑 / 视图 / 运行 | 保存、发布、撤销、重做、吸附、模式切换已有按钮；菜单数量超过实际独立任务数量 |
| 28px 菜单 + 36px 工具栏 + 28px 文档条 | 单文档仍占三行；返回同时出现在文件菜单、工作台按钮、关闭按钮 |
| 顶部与底部各一份保存状态 | 底部仅由 dirty/error 推断，不能完整表达保存中及保存期间继续编辑，增加状态维护分叉 |
| “导出场景”与工作台“导出作品” | 前者只是当前 Scene JSON，后者才是含依赖的已保存作品包；名称不清楚会误导迁移用途 |
| “工业风”作为形态目标 | 容易继续堆菜单、面板和概念；界面密度不能替代任务效率 |

## 修正原则

编辑器面向浏览器中的单文档创作，首先让用户知道在哪里创建、在哪里修改、何时已保存。Ignition 可提供属性绑定、选择上下文、可靠反馈等交互参考；菜单数量、窗口结构、项目树规模不成为目标。没有真实用户任务支撑的分类不显示，也不为假设中的复杂度预留空壳。

同一编辑页面上，一个命令有一个主要可见入口。快捷键和对象右键可以加速同一命令；跨页面的对象管理不等于重复编辑菜单。响应式收纳只迁移当前入口，不同时保留一套完整镜像。

## 本次落地

| 位置 | 职责与入口 |
| --- | --- |
| 文档页头，44px | 唯一工作台返回、名称/类型/dirty、保存与完整保存状态、适用的文档操作、布局、设计/预览 |
| 组态“文件” | 现有导入场景结构（高级）、导出场景结构（高级）；不含工具栏副本 |
| 组件页头 | 现有发布动作直接呈现；只有一个动作时不强行创建文件菜单 |
| “布局” | 左侧面板显隐、属性面板显隐、重置布局；从工具栏移除重复显隐按钮 |
| 编辑工具栏，36px | 复制、删除、撤销、重做、组合、对齐、分布、网格/吸附等现有编辑工具 |
| 左侧 | 创建、搜索、实际图层导航；不另建插入菜单 |
| 右侧 | 当前对象的属性与行为配置；组件设置保留真实入口 |
| 底部，26px | 选择、尺寸、对象数或吸附上下文；不重复保存状态 |

移除单文档页签和关闭按钮；页头名称可省略并查看完整名称。顶部由 92px 减为 80px，同时给编辑工具腾出保存、发布、布局和模式原先占用的横向空间。保留两种编辑器各自实际支持的工具，不为了对称添加功能。

返回继续走原未保存保护。保存、历史、预览门禁和布局偏好继续复用原实现。场景结构导出读取当前编辑版本；完整作品包/组件包导入导出仍在工作台，并使用现有依赖校验流程。本次没有增加新的包导入、自动保存、发布或运行协议。

## 后续设计的约束

1. D2 先整理右侧实际配置任务：明确选择范围、常用属性直接编辑、绑定详情按需展开。不能通过更多标签、长说明或嵌套卡片补偿命名问题。
2. 属性默认文案使用“静态配置、运行属性、设计值”等用户语言；类型 key、authored、fallback、schema 与父级内部标识进入确有用途的高级详情。当前右侧仍有这类遗留，未在本次全面改写。
3. 工具数量确实造成负担时，按使用频率与选择上下文收纳。例如排列可由一个明确入口展开，但不能保留整排按钮再增加一套排列菜单。
4. 完整包操作如将来迁入编辑器，须先明确“当前编辑快照/已保存版本”和依赖闭包，并迁移入口职责；不能把 Scene JSON 简单改名为“作品包”。
5. 小窗口面板覆盖、完整浏览器缩放/DPR、Firefox 仍需独立验收，不能因为页头在窄窗口可用就宣称整套编辑器已适配手机。
6. 当前 SCADA“适应场景”调用 `fillContentToViewport`，按填满而非完整容纳计算缩放，会裁切场景边缘。后续需明确“适合画板”与“填满”的任务语义；本次保留既有视口行为，浏览器多选夹具显式恢复 100% 并校验点击点在画布内。
