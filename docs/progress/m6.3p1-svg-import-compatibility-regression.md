# M6.3P1 SVG import compatibility regression

Status: **dogfooding corrective patch · 2026-09-05**

## Trigger

Immediately after M6.3P1 closeout, real local SVG assets failed to import with errors such as:

```text
SVG 包含不支持的元素 <style>
```

and then, after the first compatibility slice:

```text
<svg> 包含不支持的 style 声明：enable-background
```

The deployed M6.3P1 acceptance fixture was intentionally small and hand-authored. It proved managed SVG authority, stable tag identity, tag authoring, portability and standalone parity, but it did not prove representative compatibility with common Illustrator/Inkscape/material-library SVG export patterns.

The defect therefore does not invalidate the renderer/runtime authority decisions, but it does invalidate the practical product assumption that the original retained-element/attribute whitelist was broad enough for normal dogfooding.

## Root cause

`src/component-system/managedSvg.ts` originally used one strict retained subset for two different concerns:

1. unsafe/executable/external SVG behavior;
2. the much narrower SCADA authoring and Visual Rule surface.

That made harmless static SVG semantics fail simply because the editor did not understand them as editable fields.

The first correction added a transient compatibility pass for common `<style>` + `.class/#id` exports and editor metadata. Real assets then exposed the deeper problem: declarations such as `enable-background`, structural filter/mask elements and ordinary presentation attributes still hit the same canonical whitelist.

The corrected model is now:

```text
safe to import != editable != Visual Rule targetable
```

## Corrective boundary

The import path remains one authority chain:

```text
local SVG source
    ↓ compatibility normalization (transient)
static stylesheet/class expansion
known non-rendering editor metadata removal
    ↓
parseManagedSvgSource()
    ↓ canonical safety validation + managed normalization
ManagedSvgDocument
    ↓
existing serializer / visual rules / renderer / M8 closure
```

The compatibility pass is not persisted and is not runtime authority.

`ManagedSvgDocument` remains the only persisted internal SVG authority. `assetRef` remains its deterministic derivative. The Composite renderer, Visual Rule evaluator, M8 resource closure and M9 Attribute/Property separation are unchanged.

The detailed authority correction is recorded in:

`docs/progress/m6.3p1-svg-safe-passthrough-authority-amendment.md`

## Supported compatibility expansion

### Static stylesheet normalization

The compatibility pass supports static stylesheet rules using simple selectors:

- element selector (`path`)
- class selector (`.st0`)
- id selector (`#lamp`)
- simple combinations such as `path.st0`
- comma-separated selector lists

Static declarations are expanded onto matched elements. Declarations already owned by the managed presentation model normalize into first-class attributes. Safe non-controlled declarations may survive as deterministic residual style on the same managed element.

This means declarations such as:

```text
enable-background:new 0 0 512 512
shape-rendering:geometricPrecision
paint-order:stroke fill markers
```

no longer fail merely because they are not SCADA editable fields.

### Static SVG structure and attributes

The canonical parser now treats the SCADA editing subset separately from the SVG safety boundary.

Safe static SVG namespace structure can pass through the managed document, including common structures such as:

- `mask`
- `pattern`
- `marker`
- `filter`
- common `fe*` filter primitives
- `image` / `feImage` with self-contained raster data or internal references

Safe non-event, non-namespaced attributes may be retained even when the editor does not expose them.

Internal `url(#...)` references remain referentially validated against IDs inside the same managed document.

### Non-rendering editor metadata

Known compatibility metadata is still discarded before canonical parsing:

- SVG `<metadata>` subtrees
- Inkscape namespace elements/attributes
- Sodipodi namespace elements/attributes
- `class` after stylesheet expansion
- non-rendering `data-*`, `aria-*`, `role`, `focusable`, `tabindex` compatibility metadata

## Authoring/rule authority remains narrow

Importability does not widen the SCADA authoring contract.

The existing tag editor and Visual Rule target surface remains limited to the controlled presentation fields already accepted by M6.3P1, including the user-facing edit subset:

- `fill`
- `stroke`
- `stroke-width`
- `opacity`

Passthrough attributes/styles are retained for visual fidelity, not promoted to public Attribute/Property or arbitrary rule targets.

## Still fail-closed

The corrected model intentionally continues to reject:

- `script`, event handlers and executable SVG behavior;
- `foreignObject`;
- SVG animation elements and other dynamic execution constructs;
- DTD/entity input and unsupported processing instructions;
- external HTTP/file/blob resources;
- non-internal CSS `url(...)` resources;
- CSS `@import`, `@font-face`, `@media`, keyframes and other at-rules;
- complex selectors requiring descendant/sibling/pseudo-selector runtime semantics;
- `!important`, CSS custom-property authority and declarations that cannot be deterministically normalized;
- non-SVG visible namespace content not explicitly discarded as editor metadata.

This correction broadens static compatibility without creating a second CSS/DOM runtime authority.

## Acceptance guard

`scripts/pages-svg-import-compatibility-smoke.mjs` now covers:

- `<style>` using class and id selectors;
- class-driven fill/stroke/stroke-width;
- id-driven opacity;
- root `enable-background` and `shape-rendering` residual style;
- stylesheet `paint-order` passthrough;
- Inkscape label metadata;
- Sodipodi named-view metadata;
- static mask/filter/filter-primitive structure and internal references;
- an unsafe stylesheet with an external URL that must still fail closed.

The smoke verifies the normal asset imports as managed SVG, preserves the existing editable presentation values, accepts representative static passthrough semantics, and keeps external-resource behavior blocked.

This is a post-closeout corrective defect, not a new milestone and not authorization to reopen M8/M9 or introduce another renderer/runtime path.
