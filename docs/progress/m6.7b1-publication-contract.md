# M6.7B1 Publication contract + immutable revision store

Status: accepted implementation gate · 2026-08-29

## Goal

Define and verify the first remote component publication contract without turning the backend into SCADA runtime authority or conflating local authoring state with remote publication state.

M6.7A already established the runtime convergence point:

```text
validated package
        ↓
ComponentRegistration
        ↓
ComponentRegistry
```

M6.7B1 therefore owns only package distribution identity, immutable revision history, optimistic concurrency, idempotency, and retrieval.

## Local state is not publication state

`ComponentLibraryEntry.status` remains a local authoring/runtime-readiness flag:

```text
draft
ready
```

It does not gain a `published` meaning.

An explicit publish operation converts a local `ready` entry into a distributable package that intentionally excludes local workspace metadata:

```text
local-only                    published package
---------                     -----------------
id                      X
status                  X
updatedAt               X
builtIn                 X
                              packageVersion
                              definition
                              visual
                              implementationDraft
```

`implementationDraft` remains inert package content. Publication does not make it executable.

## Versioned wire contract

Publication schema version: `1`.

Publish request:

```text
schemaVersion
requestId
componentType
baseRevision
package
```

Published revision:

```text
schemaVersion
revisionId
requestId
componentType
revision
package
publishedAt
```

Publication head/list projection:

```text
schemaVersion
componentType
title
latestRevision
latestRevisionId
publishedAt
```

`componentType` in the request/envelope must match `package.definition.type`.

A retrieved revision is converted into a synthetic non-built-in `ready` ComponentLibraryEntry before it enters the existing package validation / M6.7A activation path. Remote origin therefore does not create a second renderer/runtime architecture.

## Immutable revision semantics

The new publication authority is `component_publication_revisions`.

Each successful publish appends one immutable row with:

- revision identity
- idempotency request identity
- component type
- monotonic per-type revision number
- base revision
- list title projection
- JSONB package
- publication timestamp

Published rows are never updated by the publication API.

The previous mutable `components` table is left untouched for non-destructive migration safety but is no longer the M6.7B publication authority.

## Optimistic concurrency

A publisher sends the remote revision on which its next publication is based:

```text
new component:      baseRevision = null
existing component: baseRevision = current remote revision
```

The server serializes publication decisions per component type in one PostgreSQL transaction.

If the server's current revision does not equal `baseRevision`, publication returns:

```text
409 publication_conflict
currentRevision = <server value or null>
```

No silent overwrite or last-writer-wins policy is allowed.

## Idempotency

`requestId` is the publication idempotency key.

The server serializes the same request identity before checking prior publication state.

- same requestId + same type/base/package: return the already-created revision
- same requestId + different publication input: `409 idempotency_conflict`

A network retry can therefore be safe without creating duplicate revisions.

## API

Public reads:

- `GET /api/component-publications`
- `GET /api/component-publications/:componentType`
- `GET /api/component-publications/:componentType/revisions/:revision`

Authenticated write:

- `POST /api/component-publications/:componentType/revisions`

There is intentionally no `PUT` for a published revision and no publication DELETE path in B1.

The existing bearer admin token is retained only as a development/server boundary. It must not be embedded into the public browser application; browser identity/authentication belongs to M6.7B2.

## Verification

### Pure browser/domain contract

`scripts/check-component-publication-contract.ts` verifies:

- local-only metadata is excluded from the distributable package
- only local `ready` packages create publication requests
- requestId/baseRevision validation
- request/package component type consistency
- published revision parsing
- remote revision -> local activation-candidate conversion

### Pure server wire contract

`scripts/check-server-publication-contract.mjs` verifies:

- request/package/route type agreement
- base-revision shape
- revision parameter validation
- server response envelope compatibility

### PostgreSQL + Fastify integration

CI includes a dedicated `publication-api` job using PostgreSQL 16 and the real Fastify service.

It verifies:

1. empty publication list
2. publish revision 1
3. identical request retry returns the same revision
4. reused requestId with different payload returns idempotency conflict
5. stale baseRevision returns publication conflict and current revision
6. publish revision 2 from base revision 1
7. latest lookup returns revision 2
8. explicit revision 1 lookup still returns the original revision-1 package
9. list/head projection points to revision 2
10. route/request type mismatch is rejected

CI #672 passed both the normal verify job and the real PostgreSQL publication-api job.

## Accepted boundary

M6.7B1 does not include:

- browser publish UI
- browser credential/token persistence
- end-user authentication
- remote package cache/synchronization
- automatic publication on local save
- production backend deployment
- package marketplace/discovery
- mutable published artifacts
- remote SCADA runtime evaluation

## Next gate

M6.7B2 Client publication/retrieval integration should now define the browser-facing remote repository and authentication boundary, then decide whether production deployment is justified.

The required invariant remains:

> Local save is local. Publish is explicit. Published revisions are immutable. Retrieved packages are validated on the client and enter the same M6.7A activation path as local packages.
