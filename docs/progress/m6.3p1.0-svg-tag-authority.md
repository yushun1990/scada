# M6.3P1.0 — SVG asset/tag authority freeze

Status: **authority freeze proposed · 2026-09-04**

This gate is the required authority decision before any M6.3P1 upload UI is implemented.

It is a corrective extension of the accepted M6 component visual model. It does **not** reopen M8 packaging/runtime closure, M9 Attribute/Property authority, or authorize M10.

## 1. Re-audit of current authority

### 1.1 `SvgVisualLayer`

Current `src/component-system/visual.ts` is visual schema version `3`.

`SvgVisualLayer` currently persists only:

```text
kind = svg
assetRef
outer layer transform / visibility / opacity
asset style.fit
```

There is no persisted SVG document, internal tag identity, internal presentation authority or internal target surface.

### 1.2 Composite renderer

`src/component-system/CompositeComponentVisualRenderer.tsx` is still the accepted reusable renderer boundary established by M6.3.0.

Today SVG and Image layers share `VisualAssetLayer`:

```text
assetRef
  ↓ browser Image
HTMLImageElement
  ↓
Konva.Image
```

The renderer does not materialize SVG tags as React, DOM or Konva child nodes. Therefore internal SVG authoring cannot legitimately target runtime DOM selectors or invent a second SVG renderer without violating the existing boundary.

### 1.3 Visual Rule target authority

`src/component-system/visualRules.ts` currently resolves rules as:

```text
Property condition
  ↓
layerId + typed target field
  ↓
resolved ComponentVisualDefinition snapshot
  ↓
Composite renderer
```

Rule conditions remain Property-driven. Target values may use the explicit M9 `attribute` or `property` namespace through `valueSource`.

The current target address is layer-only; SVG/Image layers expose only the common outer-layer fields plus `style.fit`.

### 1.4 Runtime ordering

`src/component-system/composite-registration.tsx` confirms one current execution chain:

```text
Authored ComponentVisualDefinition
  ↓ resolveComponentVisualRules(attributes, properties)
Rule-resolved visual snapshot
  ↓ evaluate/apply Visual Animation overlay
Rendered visual snapshot
  ↓
CompositeComponentVisualRenderer
```

M6.3P1 must extend this chain rather than create a parallel SVG rule/runtime path.

### 1.5 M8 visual-resource closure

M8A4 remains accepted authority.

At the distribution boundary every SVG/Image layer must carry a self-contained supported `data:image/...` `assetRef`. Relative, root-relative, remote HTTP(S), blob and non-image data references fail closed.

The current distributable component envelope is package version `2` after M9, but the M8 resource-closure rule itself is unchanged and is still enforced through `src/features/component-library/distributable-component-package.ts`.

M6.3P1 must not introduce:

- a second resource table;
- package-owned multi-file SVG dependencies;
- remote resource fetching;
- host-relative nested SVG resources;
- a standalone-only asset resolver.

## 2. Authority decision

M6.3P1 adopts a **managed SVG document nested inside the existing `SvgVisualLayer`**.

For a managed imported SVG:

```text
SvgVisualLayer
├── assetRef              derived self-contained M8 compatibility/render artifact
├── document              canonical persisted SVG authority
├── outer transform
├── outer visible/opacity
└── outer style.fit
```

The managed `document` is the single authority for SVG internal structure, stable tag identity and authored internal presentation.

`assetRef` is **not** an independent second source of truth for a managed SVG. It is the deterministic `data:image/svg+xml,...` serialization of the authored base document and must validate as such at persistence/distribution boundaries.

Legacy/opaque SVG layers may continue to have `assetRef` without a managed `document`. They retain current whole-image behavior and expose no internal tag authoring until an explicit managed import/replace operation creates the document.

This allows backward compatibility without silently reparsing or reclassifying old local assets.

## 3. Canonical persisted document

The implementation slice following this freeze should introduce a visual schema version bump (`3 -> 4`) and a renderer-independent private model equivalent to:

```ts
type ManagedSvgDocument = {
  version: 1
  root: ManagedSvgElement
}

type ManagedSvgElement = {
  kind: 'element'
  tagName: string
  tagId: string
  attributes: readonly ManagedSvgAttribute[]
  children: readonly ManagedSvgNode[]
}

type ManagedSvgText = {
  kind: 'text'
  text: string
}

type ManagedSvgNode = ManagedSvgElement | ManagedSvgText

type ManagedSvgAttribute = {
  name: string
  value: string
}
```

The exact TypeScript names may change, but the authority rules below may not.

### 3.1 Structural authority

- child order is SVG paint/source order;
- every retained element owns one stable private `tagId`;
- attributes are normalized into a deterministic unique order;
- text nodes preserve accepted text content/order;
- no React element, DOM `Node`, Konva node, CSS selector or XPath is persisted;
- original SVG `id` may be preserved as ordinary safe source metadata/reference data, but it is never SCADA target identity.

### 3.2 Stable tag identity

On first managed import:

1. parse and sanitize the source;
2. traverse the accepted sanitized element tree in document preorder;
3. assign `svg-tag-000001`, `svg-tag-000002`, ...;
4. persist those IDs in the managed document;
5. never recompute IDs merely because the component is saved, reopened, packaged or loaded by standalone runtime.

A source-provided `data-scada-tag` is reserved and must not be trusted as authority. It is removed before IDs are assigned.

Canonical SVG serialization may emit the persisted private ID as `data-scada-tag="..."` for deterministic transport/debug evidence, but the persisted managed document remains the authority.

A future structural editor must preserve existing IDs when moving/reordering retained nodes and allocate new IDs only to genuinely new elements. M6.3P1 does not authorize path-point or arbitrary structure creation.

## 4. Static SVG tag authoring authority

Static tag edits mutate the **authored managed document itself**.

M6.3P1 must not add a second sidecar style/override tree that can disagree with the SVG document.

For example, editing the lamp fill changes the controlled `fill` attribute on the managed element with `tagId = svg-tag-000005` and regenerates the base `assetRef` deterministically.

This gives one authored truth:

```text
managed document attributes
  ↓ canonical SVG serializer
base assetRef
```

The initial editable/targetable presentation subset is intentionally narrow:

- `fill`
- `stroke`
- `stroke-width`
- `opacity`

The authoring UI may expose friendly names, but it writes only this controlled private SVG surface.

Additional SVG presentation fields require an explicit later extension of the same managed-document model; they must not be tunneled through arbitrary attribute editing.

## 5. Sanitization and unsupported SVG behavior

Managed SVG is a **safe SVG subset**, not arbitrary browser SVG execution.

Sanitization happens at the import boundary before the document becomes package state. A transient parser implementation may use browser XML facilities internally, but parser/DOM object identity is not persisted, exposed to rules or used as runtime target authority.

### 5.1 Required safe baseline

The first managed-import implementation must support the industrial-icon baseline needed by this patch, including nested:

- `svg`
- `g`
- `path`
- `rect`
- `circle`
- `ellipse`
- `line`
- `polyline`
- `polygon`

Safe definition/presentation support may include a centrally allowlisted subset such as gradients and clipping, but it must go through the same validator/serializer and cannot create another execution path.

### 5.2 Must fail closed

The managed import must reject, rather than execute or preserve as opaque active behavior:

- `script`;
- `foreignObject`;
- SVG animation elements such as `animate`, `animateTransform` and `set`;
- `on*` event attributes;
- DTD/entity expansion or processing instructions with executable/external semantics;
- external HTTP(S), host-relative, file or blob references;
- nested resource references that would make the asset depend on resources outside the self-contained package;
- unsupported CSS capable of external URLs or behavior outside the controlled presentation subset.

Internal fragment references may be supported only when both endpoints are contained in and validated with the same managed document.

Comments and non-semantic editor metadata may be discarded during normalization. Unsupported visible/semantic content must not be silently dropped to produce a misleading asset; the import should fail with a user-readable reason.

Inline `style` may only be accepted when the importer can normalize every declaration into the centrally allowlisted presentation attributes. Otherwise the import fails closed.

## 6. Canonical serialization

Managed SVG serialization is deterministic.

At minimum it must fix:

- SVG namespace output;
- element/child order from the document;
- attribute ordering;
- reserved `data-scada-tag` emission;
- XML escaping;
- a single `data:image/svg+xml;charset=utf-8,${encodeURIComponent(xml)}` representation.

For an authored managed SVG layer:

```text
assetRef == serializeManagedSvgDocument(document)
```

must be a validation invariant before save/distribution.

Runtime Visual Rule results do **not** overwrite the persisted base `assetRef`; the renderer serializes the resolved in-memory document snapshot for that render.

## 7. Visual Rule internal target authority

Existing Visual Rules remain the only declarative Property-driven visual rule mechanism.

To preserve the current wire shape and minimize migration, SVG internal targeting extends the existing address with one optional private field:

```text
layerId
svgTagId?      ← optional, only valid for managed SVG layers
target
```

This is the controlled visual address for M6.3P1:

```text
(layerId, svgTagId?)
```

It is deliberately **not**:

- a DOM selector;
- source SVG `id` lookup authority;
- XPath;
- Konva node ID;
- React ref;
- arbitrary attribute path.

### 7.1 Existing layer target semantics

If `svgTagId` is absent, current behavior is unchanged. The rule targets the outer Component Visual Layer and existing target eligibility remains authoritative.

### 7.2 Managed SVG tag target semantics

If `svgTagId` is present:

- `layerId` must resolve to `kind = svg`;
- that layer must own a managed document;
- `svgTagId` must resolve to exactly one retained element;
- the target must belong to the controlled SVG-tag target subset;
- target value and optional M9 `valueSource` must type-check before the package is accepted.

Initial tag rule targets are:

```text
style.fill
style.stroke
style.strokeWidth
opacity
```

They map to the controlled SVG presentation attributes `fill`, `stroke`, `stroke-width` and `opacity` on the resolved managed document snapshot.

Rules continue to execute in serialized order; later matching rules win for the same `(layerId, svgTagId, target)` address.

Rule conditions remain Property-driven, and target values continue to preserve the explicit M9 `attribute` / `property` namespace. SVG tag targeting does not flatten or redefine either public authority.

### 7.3 Referential integrity

Save/package validation fails closed when a rule references a missing managed tag.

Replacing an SVG document is a structural replacement. The authoring operation must reconcile rules targeting removed tag IDs before the replacement can become valid package state, using the same fail-closed principle already used for deleted visual layers.

## 8. Runtime/rendering authority

The accepted runtime remains:

```text
ComponentVisualDefinition
  ↓ Visual Rule resolution
resolved ComponentVisualDefinition
  ↓ existing layer Animation overlay
rendered ComponentVisualDefinition
  ↓
CompositeComponentVisualRenderer
  ↓
Konva
```

For a managed SVG layer, the Composite renderer receives the resolved document and obtains its final image source through a pure managed-SVG serializer before the existing browser Image / `Konva.Image` path.

Conceptually:

```text
resolved SvgVisualLayer.document
  ↓ serializeManagedSvgDocument()
resolved data:image/svg+xml URL
  ↓ existing VisualAssetLayer image loading
Konva.Image
```

There is still one Component renderer and one visual-resolution pipeline.

M6.3P1 must **not** create:

- a DOM-mounted SVG runtime beside Konva;
- per-tag React SVG rendering beside `VisualAssetLayer`;
- a second rule evaluator;
- a standalone-only SVG renderer;
- a package/runtime SVG selector service.

A serializer/cache helper inside `component-system` is a controlled extension of the current renderer boundary, not a second renderer authority.

## 9. Runtime cost boundary

Property-driven tag presentation changes are expected to be discrete state changes. Re-serializing a managed SVG and refreshing its single image source when the resolved document changes is acceptable for M6.3P1.

The implementation should memoize/canonicalize by resolved managed document so an unchanged visual does not regenerate/reload the image source unnecessarily.

This decision intentionally does **not** claim that the rasterized-image path is appropriate for per-frame internal SVG animation.

## 10. SVG-tag animation decision

**Deferred from M6.3P1.**

The current M6.4 animation authority is layer-scoped: `VisualRuntimeOverlay` is keyed by `layerId` and composes controlled transform/opacity/visibility contributions.

Adding SVG tag animation now would either:

- force per-frame SVG serialization/image reload; or
- require a new per-tag renderer/runtime path; or
- widen the accepted M6.4 runtime overlay address semantics.

That is not required to close the product authoring gap and would risk reopening accepted runtime authority.

M6.3P1 therefore authorizes static tag authoring and Property-driven tag Visual Rules only. Any future element-level animation must first prove it can reuse the same controlled visual address and accepted animation execution model without creating a second runtime authority.

## 11. Schema and migration decision

Implementation after acceptance of this freeze should use:

```text
ComponentVisualDefinition version 3 -> 4
```

Migration rules:

- existing v1/v2 migration behavior remains intact;
- existing v3 layers/rules/animations preserve their current semantics;
- a v3 SVG layer migrates to v4 as an **opaque SVG** with the same `assetRef` and no managed document;
- migration does not parse arbitrary historical SVG refs or fetch resources;
- existing Visual Rules migrate unchanged with no `svgTagId`;
- only an explicit managed import/replace operation creates a managed SVG document.

The distributable component package remains current package version `2`; the visual sub-schema owns this migration. No M8 work-package envelope or standalone contract change is required.

## 12. M8 closure interaction

For managed SVG, M8 closure becomes stricter without changing ownership:

```text
managed document
  ↓ deterministic serializer
assetRef = self-contained data:image/svg+xml,...
  ↓ existing distributable package resource gate
component package / work package / standalone runtime
```

The same shared package codec remains the distribution authority.

A managed SVG package is invalid when:

- its base `assetRef` is not self-contained;
- `assetRef` does not match canonical serialization of the authored managed document;
- the managed document violates the safe subset;
- a Visual Rule references a missing/unsupported tag target.

No new resource table, file dependency or network fetch is introduced.

## 13. M9 boundary interaction

M6.3P1 changes only private visual implementation data.

It does not change:

- Component Attribute meaning as authored/static public configuration;
- Component Property meaning as runtime/point-driven public semantics;
- Property-driven Visual Rule conditions;
- explicit `valueSource.namespace = attribute | property`;
- effective Property runtime authority in Studio/standalone.

A tag ID is private visual identity. It is not a Property, Attribute, binding key or public component contract.

## 14. Normative proof fixture

The source fixture for this freeze is:

`docs/progress/fixtures/m6.3p1.0-nested-svg.svg`

It contains nested groups plus independently colorable `rect`, `circle` and `path` elements.

After sanitization, preorder identity is expected to be stable as:

```text
svg      -> svg-tag-000001
housing  -> svg-tag-000002
a shell rect -> svg-tag-000003
status   -> svg-tag-000004
lamp     -> svg-tag-000005
needle   -> svg-tag-000006
```

The source labels above come from ordinary SVG `id` attributes only for human-readable proof. Runtime target authority is the generated `svg-tag-*` identity.

At minimum the later implementation evidence must prove these two independent targets:

```text
(layerId = imported-svg, svgTagId = svg-tag-000005, target = style.fill)
(layerId = imported-svg, svgTagId = svg-tag-000006, target = style.fill)
```

remain attached to the same logical elements through:

1. managed import normalization;
2. component save/serialize;
3. component reopen/parse;
4. distributable component package serialize/parse;
5. enclosing SCADA work package round-trip;
6. standalone registration/runtime load.

The normalized serialization must also be deterministic: serializing the same managed document twice produces the same base `assetRef` byte-for-byte.

## 15. Acceptance checks for the implementation slices

Before M6.3P1 can be closed, automated evidence must cover:

- unsafe/external SVG behavior fails closed;
- nested source structure survives normalization;
- stable tag IDs survive save/reload and package round-trips;
- static tag edits modify the canonical document and regenerate the base asset deterministically;
- no sidecar authoring authority can conflict with document attributes;
- a Property-driven rule can update at least two independent internal tag colors;
- missing tag targets fail package validation;
- M9 Attribute-sourced rule target values still work with SVG tag targets;
- legacy opaque v3 SVG layers still render without being silently converted;
- managed SVG remains a self-contained M8 portable resource;
- Studio Preview and standalone runtime still use `createCompositeComponentRegistration()` plus `CompositeComponentVisualRenderer`;
- no DOM selector/React/Konva implementation detail enters persisted package state.

## 16. Explicit non-goals

This authority freeze does not authorize:

- upload/file-picker UI before this decision is accepted;
- global media library or resource manager;
- remote SVG fetching;
- arbitrary XML/SVG attribute editor;
- raw DOM inspector;
- CSS selector/XPath rule targets;
- full SVG specification support;
- path-point/vector drawing editor;
- SVG tag drag/resize/transform authoring;
- SVG-tag animation;
- package resource table v2/v3 work;
- M10 scene/widget capability work.

## 17. Gate result

The audit finds **no need for a second renderer/runtime authority** and **no need to weaken or move the M8/M9 boundaries**.

The corrective path is therefore valid:

```text
managed SVG document inside existing private visual model
  + stable private tag IDs
  + existing Visual Rule evaluator extended with optional svgTagId
  + deterministic SVG serializer
  + existing Composite renderer image path
  + existing M8 self-contained package closure
  + existing M9 Attribute/Property namespaces
```

After this authority freeze is accepted, the next implementation slice is **M6.3P1.1 Local visual asset ingest + replace**. Upload UI must be built against this managed-document contract, not used to discover the contract afterward.
