# M6.6 Local persistence foundation

Status: acceptance closeout

Date: 2026-08-28

## Goal

Move normal browser authoring away from feature-owned `localStorage` state and establish one explicit local persistence boundary that can grow without making a backend mandatory.

## Accepted architecture

```text
Workspace / Editors
        ↓
async domain storage services
        ↓
SceneRepository / ComponentRepository
        ├─ IndexedDB       browser authoring
        └─ Memory          deterministic tests
```

The physical browser authority is one versioned IndexedDB database. `localStorage` is migration input only and is not a continuing write target.

## M6.6A — repository boundary

Accepted work:

- async `SceneRepository` and `ComponentRepository` contracts
- explicit JSON document records separated from domain validation
- deterministic Memory implementations
- clone/isolation semantics at repository boundaries
- deterministic ordering
- pre-mutation duplicate validation for replacement
- versioned portable debug snapshot schema
- import/export/reset through the same repository contracts
- deterministic repository and snapshot fixtures in CI

The repository API was async from the beginning so IndexedDB did not need a later synchronous facade or fire-and-forget storage abstraction.

## M6.6B — IndexedDB browser cutover

Accepted work:

- one versioned `scada-editor-lab` IndexedDB database
- `scenes`, `components`, and `meta` object stores
- IndexedDB implementations of the accepted repository contracts
- transactional per-store replacement
- atomic Scene + Component debug snapshot replacement
- storage diagnostics and reset
- explicit legacy migration metadata
- deterministic migration planning for supported SCADA Work and Component Library `localStorage` formats
- current component package data taking precedence over historical v1 data
- domain-owned Scene/Component canonicalization during migration
- corrupt neighboring legacy documents isolated rather than poisoning valid records
- Workspace async reads/creation backed by repositories
- SCADA Editor and Component Editor hydration gates before synchronous editor/history initialization
- Workspace controls for diagnostics, debug snapshot export/import, and local reset

A populated IndexedDB is never overwritten merely because the migration marker is absent. Reset preserves migration intent so stale legacy localStorage is not silently re-imported into the same database lifecycle.

## M6.6C — async save lifecycle closeout

The final acceptance gap after the IndexedDB cutover was the two editor Save buttons. They still used compatibility adapters that updated an in-memory cache and started the IndexedDB write without awaiting it.

That compatibility path is removed.

Accepted Save semantics are now:

```text
user clicks Save
        ↓
serialize + validate current document
        ↓
await repository put
        ↓ success
update cache / show “saved”
```

On persistence failure the editor reports failure directly. It must not display a success message before durable local storage has accepted the write.

The synchronous `saveScadaScene` and `saveComponentDefinition` compatibility adapters are deleted. New callers use only `saveScadaSceneAsync` and `saveComponentDefinitionAsync`.

## Debugging boundary

A browser-only persistence problem can be converted into a portable debug snapshot containing structured Scene and Component documents. The snapshot is versioned and validated before repository mutation.

This remains the preferred debugging bridge instead of requiring a deployed backend merely to inspect local authoring state.

## Boundary after acceptance

M6.6 does not make user-authored component packages executable in SCADA merely because they are persisted. Today custom Component Workbench packages are stored correctly, but runtime registration is still built-in-only.

That boundary becomes the next milestone: M6.7 User component registration / publication.

The first M6.7 slice should prove local activation from the same IndexedDB package repository into the generic ComponentRegistry before adding a remote publication server. Remote publication should change package origin/lifecycle, not require a second runtime architecture.
