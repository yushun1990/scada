# M6.4 Animation Foundation

Status: **M6.4.1 spin runtime + M6.4.2 spin authoring + M6.4.3 move family accepted · 2026-08-26; M6.4 remains active** on `main`.

M6.4 adds reusable private visual animation to Component Workbench without turning authored components into Konva/DOM programs.

## Goal

A component developer can attach reusable animation behavior to a private visual Layer while SCADA Workbench continues to see only the component's public contract.

Animation families:

```text
spin        accepted
move        accepted
scale       next
pulse       later, likely reuses scale overlay semantics
fade        later
blink       later
```

## Accepted runtime boundary

The runtime pipeline is fixed:

```text
serialized base Layer state
        ↓
Visual Rules
        ↓
effective rule-resolved Layer state
        ↓
pure Animation Evaluator(timeMs, Properties)
        ↓
transient Animation Overlay
        ↓
compose effective Layer + overlay
        ↓
CompositeComponentVisualRenderer
        ↓
Konva
```

Architectural rule:

> Animation definitions are persistent; animation frames are transient.

Animation frames never update persisted `ComponentVisualDefinition.layers`, never create per-frame undo history and never expose raw `Konva.Node`, React or DOM objects as authored animation targets.

Visual Rules always resolve before animation overlays. Animations modulate the rule-resolved state rather than competing with rules through renderer-specific last-write-wins behavior.

## Serialized model

`ComponentVisualDefinition` v3 owns:

```ts
animations: readonly VisualAnimation[]
```

Accepted variants now include:

```ts
type SpinVisualAnimation = {
  id: string
  kind: 'spin'
  enabled: boolean
  layerId: string
  degreesPerIteration: number
  timing: VisualAnimationTiming
  activation: VisualAnimationActivation
}

type MoveVisualAnimation = {
  id: string
  kind: 'move'
  enabled: boolean
  layerId: string
  deltaXPerIteration: number
  deltaYPerIteration: number
  timing: VisualAnimationTiming
  activation: VisualAnimationActivation
}
```

Both use the same timing foundation:

```ts
type VisualAnimationTiming = {
  durationMs: number
  delayMs: number
  iterations: number | 'infinite'
  direction: 'normal' | 'reverse' | 'alternate' | 'alternate-reverse'
  easing: 'linear' | 'ease-in' | 'ease-out' | 'ease-in-out'
}
```

And the same activation foundation:

```ts
type VisualAnimationActivation =
  | { kind: 'always' }
  | {
      kind: 'property'
      propertyKey: string
      operator: VisualRuleOperator
      compareValue: ComponentScalarValue
    }
```

Property activation deliberately reuses Visual Rule condition/operator semantics rather than introducing another expression language.

Adding `move` did not require another visual schema bump: v3 already owns a discriminated animation collection and the additional family extends that vocabulary.

## Overlay composition

`src/component-system/animations.ts` remains renderer-independent model code and imports no React or Konva API.

The accepted overlay channels are now:

```ts
type VisualAnimationLayerOverlay = {
  rotationDelta?: number
  translateX?: number
  translateY?: number
}
```

Composition rules:

```text
rotation deltas          add
translation deltas       add
scale multipliers        future: multiply
opacity multipliers      future: multiply
visibility overrides     future: deterministic boolean composition
```

Spin animations targeting the same Layer add their rotation deltas. Move animations targeting the same Layer add their X/Y translation deltas. Neither family mutates the rule-resolved or persisted base Layer.

Examples:

```text
base x from serialized Layer  = 10
Visual Rule resolves x        = 100
move overlay                  = +30
rendered x                    = 130
persisted x                   = 10
```

```text
serialized rotation           = 20
Visual Rule resolves rotation = 40
spin overlay                  = +180
rendered rotation             = 220
persisted rotation            = 20
```

## Validation

`assertComponentVisualAnimations(definition, visual)` validates semantic animation references after structural visual validation.

Accepted checks include:

- unique, non-empty animation ids
- supported kind: `spin` or `move`
- existing Layer target
- finite `degreesPerIteration` for spin
- finite `deltaXPerIteration` / `deltaYPerIteration` for move
- positive finite duration
- non-negative finite delay
- positive integer finite iterations or `infinite`
- bounded direction/easing vocabulary
- valid Property references for conditional activation
- compare values compatible with Property type
- numeric-only relational operators

The Renderer performs none of this validation or condition evaluation.

## Preview clock boundary

Animation math receives explicit `timeMs`; it does not read clocks itself.

```text
Component Preview host
  owns requestAnimationFrame + elapsed epoch
        ↓
pure animation evaluator(timeMs)
        ↓
transient overlay
```

Lifecycle remains:

- Design mode does not run animations
- entering Preview starts an epoch at `t = 0`
- leaving Preview stops the frame loop and clears transient time
- re-entering Preview restarts at `t = 0`
- Property changes re-evaluate activation against the current Preview epoch
- no animation frame invokes the package `onChange` path

## Migration and reference reconciliation

Stored visual migration remains:

```text
v1 -> v3
  restore designSize
  animations: []

v2 -> v3
  preserve designSize/rules/layers
  animations: []

v3 -> validate directly
```

Animation references use stable ids and stable `layerId` targets. Workbench operations preserve the same integrity expected from Visual Rules:

- Layer rename rewrites animation target ids
- Layer deletion removes orphaned animations
- cloning a Layer subtree clones/re-targets animations for cloned Layers
- grouping preserves child-targeted animations
- ungrouping removes animation targeting a deleted Group wrapper while preserving child-targeted animations
- Property rename/delete reconciles Property-activated animations
- incompatible Property type/operator changes fall back to a valid condition shape

## Renderer boundary

`CompositeComponentVisualRenderer` still receives effective visual state and draws it.

It does **not**:

- parse animation definitions
- own authored timing semantics
- inspect Property activation conditions
- call `requestAnimationFrame`
- expose Konva nodes as authored animation targets
- persist animated values

This remains the boundary required for M6.5 Controlled Script Runtime, which can later operate on stable animation ids instead of renderer objects.

## Next slice: M6.4.4 Scale animation family

The next focused slice should prove the third semantic composition channel: **multiplicative scale overlays**.

Proposed primitive shape:

```ts
type ScaleVisualAnimation = {
  id: string
  kind: 'scale'
  enabled: boolean
  layerId: string
  scaleXMultiplier: number
  scaleYMultiplier: number
  timing: VisualAnimationTiming
  activation: VisualAnimationActivation
}
```

Evaluation should interpolate from identity multiplier `1` toward the authored target multiplier:

```text
currentScaleXMultiplier = 1 + (targetScaleXMultiplier - 1) * progress
currentScaleYMultiplier = 1 + (targetScaleYMultiplier - 1) * progress
```

Composition must be multiplicative:

```text
Visual Rule resolved scale × animation multiplier(s) = rendered scale
```

Multiple Scale animations targeting one Layer multiply rather than overwrite each other. `alternate` timing naturally gives grow/shrink behavior, allowing a later `pulse` family to reuse or specialize the same scale overlay channel instead of inventing incompatible semantics.

M6.4.4 must preserve:

- no visual schema bump unless a real migration requirement appears
- definitions remain serializable private implementation
- runtime frames remain transient overlays
- Visual Rules resolve before Scale overlays
- authoring UI edits definitions only
- Renderer remains unaware of authored timing/Property activation
- no keyframe/timeline system

## Future Controlled Script Runtime compatibility

M6.5 may later expose controlled operations such as:

```text
startAnimation(animationId)
stopAnimation(animationId)
restartAnimation(animationId)
```

That API should operate on stable animation ids and must never return or accept `Konva.Node`, DOM or React objects.

## Deferred / non-goals

- arbitrary keyframe editor
- timeline sequencing UI
- CSS animation import
- arbitrary cubic-bezier strings
- spring/physics simulation
- Action/Event-triggered animation orchestration
- unrestricted script callbacks
- raw Konva Tween exposure
- Web Animations API as authored component contract
- animation frame persistence into `ComponentVisualDefinition`
- SCADA-specific animation authoring
