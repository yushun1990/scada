# M6.4 Animation Foundation

Status: **M6.4.1 Spin runtime + M6.4.2 Spin authoring + M6.4.3 Move + M6.4.4 Scale + M6.4.5 Fade accepted · 2026-08-26; M6.4 remains active** on `main`.

M6.4 is a visual-runtime capability experiment for Component Workbench. The named families (`spin`, `move`, `scale`, `fade`, next `blink`) are deliberately concrete test vehicles, not a promise that the final component API will permanently expose one first-class runtime type per visual effect.

The intent is:

```text
concrete visual experiments
        ↓
prove timing / composition / lifecycle semantics
        ↓
extract generic Visual Runtime primitives
        ↓
component-private behavior composes those primitives
        ↓
component exposes stable Properties / Actions / Events
```

SCADA Workbench should consume the public component contract, not private Layer animation details.

## Goal and runtime boundary

A component developer can attach reusable visual behavior to a private visual Layer while SCADA Workbench continues to see only the component public contract.

The accepted runtime pipeline is fixed:

```text
serialized base Layer state
        ↓
Visual Rules
        ↓
effective rule-resolved Layer state
        ↓
pure Animation Evaluator(timeMs, Properties)
        ↓
transient Animation Overlay
        ↓
compose effective Layer + overlay
        ↓
CompositeComponentVisualRenderer
        ↓
Konva
```

Architectural rule:

> Animation definitions are persistent; animation frames are transient.

Animation frames never update persisted `ComponentVisualDefinition.layers`, never create per-frame undo history and never expose raw `Konva.Node`, React or DOM objects as authored animation targets. Visual Rules resolve first; animations only modulate the rule-resolved state.

## Current experiment families

```text
spin        accepted · additive rotation
move        accepted · additive x/y translation
scale       accepted · multiplicative x/y scale
fade        accepted · multiplicative opacity
blink       next     · deterministic stepped visibility / discrete-state experiment
pulse       no separate runtime primitive planned; Scale + alternate already proves its semantics
```

`ComponentVisualDefinition` remains visual schema v3. New experiment families extend the discriminated `VisualAnimation` union and do not require a schema bump by themselves.

After Blink, M6.4 should stop adding named visual-effect families and perform an explicit abstraction/consolidation pass. That pass should decide which generic visual properties/operations become the stable foundation used later by Rules, Behavior and the controlled Script Runtime.

## Shared timing and activation

Every accepted continuous family reuses:

```ts
type VisualAnimationTiming = {
  durationMs: number
  delayMs: number
  iterations: number | 'infinite'
  direction: 'normal' | 'reverse' | 'alternate' | 'alternate-reverse'
  easing: 'linear' | 'ease-in' | 'ease-out' | 'ease-in-out'
}

type VisualAnimationActivation =
  | { kind: 'always' }
  | {
      kind: 'property'
      propertyKey: string
      operator: VisualRuleOperator
      compareValue: ComponentScalarValue
    }
```

Property activation currently reuses Visual Rule condition/operator semantics. It is sufficient for the experiment stage; final control ownership can later move behind component behavior / script APIs such as `startAnimation(id)` / `stopAnimation(id)` without changing the renderer boundary.

## Accepted overlay composition

`src/component-system/animations.ts` remains renderer-independent and imports no React or Konva API.

Current overlay channels:

```ts
type VisualAnimationLayerOverlay = {
  rotationDelta?: number
  translateX?: number
  translateY?: number
  scaleXMultiplier?: number
  scaleYMultiplier?: number
  opacityMultiplier?: number
}
```

Composition semantics locked down by deterministic CI checks:

```text
rotation deltas          add
translation deltas       add
scale multipliers        multiply
opacity multipliers      multiply
visibility overrides     next: deterministic stepped composition
```

Examples:

```text
Visual Rule resolved x       = 100
Move overlay                 = +30
rendered x                   = 130
```

```text
Visual Rule resolved scaleX  = 2
Scale overlay                = ×1.5
rendered scaleX              = 3
```

```text
Visual Rule resolved opacity = 0.8
Fade overlay                 = ×0.5
rendered opacity             = 0.4
```

Positive Scale multipliers preserve the sign of a mirrored negative base scale.

## Validation and lifecycle

`assertComponentVisualAnimations(definition, visual)` validates:

- unique, non-empty animation IDs
- supported animation kinds
- existing Layer targets
- family-specific numeric constraints
- positive finite duration
- non-negative finite delay
- positive integer finite iterations or `infinite`
- bounded direction/easing vocabulary
- valid Property references and typed compare values
- numeric-only relational operators

The Preview host owns `requestAnimationFrame` and elapsed epoch. The pure evaluator receives explicit `timeMs` and never reads a clock itself.

Lifecycle remains:

- Design mode never runs animation frames
- entering Preview starts at `t = 0`
- leaving Preview stops the loop and discards transient overlays
- re-entering Preview restarts at `t = 0`
- Property changes re-evaluate activation against the current Preview epoch
- animation frames never call package `onChange`

## Migration and reference reconciliation

Stored visual migration remains:

```text
v1 -> v3: restore designSize + animations: []
v2 -> v3: preserve designSize/rules/layers + animations: []
v3 -> validate directly
```

Workbench model operations preserve animation references:

- Layer rename rewrites animation targets
- Layer deletion removes orphaned animations
- clone rewrites cloned animation IDs/targets
- Group/Ungroup preserves child-targeted animations and drops removed wrapper targets
- Property rename/delete/type changes reconcile Property-activated animations

The Renderer performs none of this reconciliation.

## Renderer boundary

`CompositeComponentVisualRenderer` only receives effective visual state and draws it. It does **not**:

- parse animation definitions
- own timing/easing semantics
- inspect Property activation
- call `requestAnimationFrame`
- expose Konva nodes as authored animation targets
- persist animated values

This boundary remains important for M6.5 Controlled Script Runtime, where future visual-control operations must address stable model concepts rather than renderer objects.

## M6.4.4 Scale animation family — accepted · 2026-08-26

Goal:

> Prove multiplicative scale composition as the third semantic overlay channel.

Implemented primitive:

```ts
type ScaleVisualAnimation = {
  id: string
  kind: 'scale'
  enabled: boolean
  layerId: string
  scaleXMultiplier: number
  scaleYMultiplier: number
  timing: VisualAnimationTiming
  activation: VisualAnimationActivation
}
```

Semantics:

```text
current multiplier = 1 + (target multiplier - 1) × eased progress
rendered scale      = rule-resolved scale × composed animation multiplier(s)
```

Design decisions:

- target X/Y multipliers must be finite and strictly greater than zero
- zero/negative authored multipliers are rejected
- existing negative base scale remains supported
- multiple Scale animations multiply
- Rules resolve scale before Scale overlay
- base transforms remain immutable

## Next slice: M6.4.6 Blink / stepped visibility experiment

Blink is the last named visual-effect experiment planned before runtime abstraction consolidation.

Goal:

> Prove deterministic discrete-state animation semantics rather than another continuous numeric interpolation channel.

The experiment should target Layer visibility through a transient overlay and should **not** fake Blink with smooth opacity interpolation.

Expected questions to settle:

- how a step/cycle maps explicit `timeMs` to visible/hidden state
- how delay, finite/infinite iterations and direction interact with discrete state
- how multiple visibility-affecting animations compose deterministically
- how Visual Rule resolved `visible` state interacts with the transient overlay
- how Property activation stops/starts the discrete result without persisting Layer state
- how Design remains static and Preview owns the clock

Do not broaden Blink into arbitrary keyframes or a generic timeline editor.

After Blink acceptance, add an explicit M6.4 abstraction/consolidation slice before M6.5. That pass should extract the proven common foundation from rotation, translation, scale, opacity and visibility instead of continuing to create named runtime effect families.

## Deferred / non-goals

- arbitrary keyframe/timeline editor
- CSS animation import
- arbitrary cubic-bezier strings
- spring/physics simulation
- unrestricted script callbacks
- raw Konva Tween exposure
- Web Animations API as authored contract
- per-frame persistence
- SCADA-specific animation authoring
- a separate Pulse runtime primitive
