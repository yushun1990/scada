# M6.4 Animation Foundation

Status: **M6.4.1 Spin runtime + M6.4.2 Spin authoring + M6.4.3 Move + M6.4.4 Scale + M6.4.5 Fade + M6.4.6 Blink accepted · 2026-08-26; M6.4.7 Visual Runtime abstraction consolidation is active** on `main`.

M6.4 is a visual-runtime capability experiment for Component Workbench. The named families (`spin`, `move`, `scale`, `fade`, `blink`) are deliberately concrete test vehicles, not a promise that the final component API will permanently expose one first-class runtime type per visual effect.

The intent is:

```text
concrete visual experiments
        ↓
prove timing / composition / lifecycle semantics
        ↓
extract generic Visual Runtime primitives
        ↓
component-private behavior composes those primitives
        ↓
component exposes stable Properties / Actions / Events
```

SCADA Workbench should consume the public component contract, not private Layer animation details.

## Goal and runtime boundary

A component developer can attach reusable visual behavior to a private visual Layer while SCADA Workbench continues to see only the component public contract.

The accepted runtime pipeline is fixed:

```text
serialized base Layer state
        ↓
Visual Rules
        ↓
effective rule-resolved Layer state
        ↓
pure Animation Evaluator(timeMs, Properties)
        ↓
transient Animation Overlay
        ↓
compose effective Layer + overlay
        ↓
CompositeComponentVisualRenderer
        ↓
Konva
```

Architectural rule:

> Animation definitions are persistent; animation frames are transient.

Animation frames never update persisted `ComponentVisualDefinition.layers`, never create per-frame undo history and never expose raw `Konva.Node`, React or DOM objects as authored animation targets. Visual Rules resolve first; animations only modulate the rule-resolved state.

## Completed experiment families

```text
spin        accepted · additive rotation
move        accepted · additive x/y translation
scale       accepted · multiplicative x/y scale
fade        accepted · multiplicative opacity
blink       accepted · deterministic stepped visibility gate
pulse       no separate runtime primitive planned; Scale + alternate already proves its semantics
```

`ComponentVisualDefinition` remains visual schema v3. The named experiment families extended the discriminated `VisualAnimation` union without requiring a schema bump.

M6.4 now stops adding named visual-effect families. M6.4.7 is an explicit abstraction/consolidation pass that extracts the generic visual properties, operations and timing semantics proven by these experiments.

## Shared timing and activation

The experiment definitions reuse:

```ts
type VisualAnimationTiming = {
  durationMs: number
  delayMs: number
  iterations: number | 'infinite'
  direction: 'normal' | 'reverse' | 'alternate' | 'alternate-reverse'
  easing: 'linear' | 'ease-in' | 'ease-out' | 'ease-in-out'
}

type VisualAnimationActivation =
  | { kind: 'always' }
  | {
      kind: 'property'
      propertyKey: string
      operator: VisualRuleOperator
      compareValue: ComponentScalarValue
    }
```

Property activation currently reuses Visual Rule condition/operator semantics. It is sufficient for the experiment stage; final control ownership can later move behind component behavior / script APIs such as stable animation/control handles without changing the renderer boundary.

The timing experiments also proved an important distinction:

```text
raw directed phase       = cycle position after delay / iteration / direction
continuous progress      = easing(raw phase)
stepped discrete state   = threshold(raw phase), without easing
```

Spin, Move, Scale and Fade consume eased continuous progress. Blink consumes raw directed phase so an easing curve cannot silently change its discrete visible/hidden duty cycle.

## Accepted overlay composition

`src/component-system/animations.ts` remains renderer-independent and imports no React or Konva API.

Current experimental overlay channels:

```ts
type VisualAnimationLayerOverlay = {
  rotationDelta?: number
  translateX?: number
  translateY?: number
  scaleXMultiplier?: number
  scaleYMultiplier?: number
  opacityMultiplier?: number
  visibleGate?: boolean
}
```

Composition semantics locked down by deterministic CI checks:

```text
rotation deltas          add
translation deltas       add
scale multipliers        multiply
opacity multipliers      multiply
visibility gates         logical AND
```

Examples:

```text
Visual Rule resolved x       = 100
Move overlay                 = +30
rendered x                   = 130
```

```text
Visual Rule resolved scaleX  = 2
Scale overlay                = ×1.5
rendered scaleX              = 3
```

```text
Visual Rule resolved opacity = 0.8
Fade overlay                 = ×0.5
rendered opacity             = 0.4
```

```text
Visual Rule resolved visible = false
Blink gate                   = true
rendered visible             = false
```

Blink is intentionally a visibility **gate**, not a force-visible override:

```text
rendered visible = rule-resolved visible && blink gate(s)
```

Therefore Blink may transiently hide content but can never reveal a Layer already hidden by persisted state or Visual Rules. Multiple Blink gates compose with logical AND.

Positive Scale multipliers preserve the sign of a mirrored negative base scale.

## Validation and lifecycle

`assertComponentVisualAnimations(definition, visual)` validates:

- unique, non-empty animation IDs
- supported animation kinds
- existing Layer targets
- family-specific numeric constraints
- positive finite duration
- non-negative finite delay
- positive integer finite iterations or `infinite`
- bounded direction/easing vocabulary
- valid Property references and typed compare values
- numeric-only relational operators

The Preview host owns `requestAnimationFrame` and elapsed epoch. The pure evaluator receives explicit `timeMs` and never reads a clock itself.

Lifecycle remains:

- Design mode never runs animation frames
- entering Preview starts at `t = 0`
- leaving Preview stops the loop and discards transient overlays
- re-entering Preview restarts at `t = 0`
- Property changes re-evaluate activation against the current Preview epoch
- finite animation completion drops its transient overlay and restores the rule/base visual state
- animation frames never call package `onChange`

## Migration and reference reconciliation

Stored visual migration remains:

```text
v1 -> v3: restore designSize + animations: []
v2 -> v3: preserve designSize/rules/layers + animations: []
v3 -> validate directly
```

Workbench model operations preserve animation references:

- Layer rename rewrites animation targets
- Layer deletion removes orphaned animations
- clone rewrites cloned animation IDs/targets
- Group/Ungroup preserves child-targeted animations and drops removed wrapper targets
- Property rename/delete/type changes reconcile Property-activated animations

The Renderer performs none of this reconciliation.

## Renderer boundary

`CompositeComponentVisualRenderer` only receives effective visual state and draws it. It does **not**:

- parse animation definitions
- own timing/easing semantics
- inspect Property activation
- call `requestAnimationFrame`
- expose Konva nodes as authored animation targets
- persist animated values

This boundary remains important for M6.5 Controlled Script Runtime, where future visual-control operations must address stable Visual Runtime model concepts rather than renderer objects.

## M6.4.4 Scale animation family — accepted · 2026-08-26

Goal:

> Prove multiplicative scale composition as the third semantic overlay channel.

Implemented primitive:

```ts
type ScaleVisualAnimation = {
  id: string
  kind: 'scale'
  enabled: boolean
  layerId: string
  scaleXMultiplier: number
  scaleYMultiplier: number
  timing: VisualAnimationTiming
  activation: VisualAnimationActivation
}
```

Semantics:

```text
current multiplier = 1 + (target multiplier - 1) × eased progress
rendered scale      = rule-resolved scale × composed animation multiplier(s)
```

Design decisions:

- target X/Y multipliers must be finite and strictly greater than zero
- zero/negative authored multipliers are rejected
- existing negative base scale remains supported
- multiple Scale animations multiply
- Rules resolve scale before Scale overlay
- base transforms remain immutable

## M6.4.6 Blink / stepped visibility experiment — accepted · 2026-08-26

Goal:

> Prove deterministic discrete-state animation semantics rather than another continuous numeric interpolation channel.

Implemented primitive:

```ts
type BlinkVisualAnimation = {
  id: string
  kind: 'blink'
  enabled: boolean
  layerId: string
  timing: VisualAnimationTiming
  activation: VisualAnimationActivation
}
```

Implemented semantics:

```text
raw phase                 = directed cycle phase in [0, 1)
Blink gate                = raw phase < 0.5
rendered visible          = rule-resolved visible && all active Blink gates
```

Key decisions and verification:

- Blink targets visibility, not opacity
- Blink uses raw directed phase instead of eased progress
- easing therefore cannot distort the visible/hidden duty cycle
- the Inspector disables easing authoring for Blink while retaining compatible timing metadata
- the first half-cycle is visible and the second half-cycle hidden
- direction deterministically transforms the stepped phase
- delay and finite/infinite iteration lifecycle reuse the accepted timing model
- finite completion removes the transient gate and restores the rule/base visual state
- multiple Blink definitions targeting one Layer compose with logical AND
- Blink can hide a rule-visible Layer but can never force a rule-hidden Layer visible
- persisted and rule-resolved `visible` remain immutable
- Property activation reuses the accepted typed condition semantics
- selected-Layer Inspector supports `+ 添加 Blink 动画`
- dedicated deterministic Blink model checks are wired into CI
- dedicated deployed Blink smoke authors through the real Inspector; it does not inject Blink JSON

## Next slice: M6.4.7 Visual Runtime abstraction consolidation

This is a required convergence slice, not optional cleanup.

Goal:

> Extract the stable low-level Visual Runtime semantics proven by the five concrete experiments without breaking the accepted renderer boundary or prematurely forcing a large package-schema migration.

The evidence now covers:

```text
continuous additive       rotation, x, y
continuous multiplicative scaleX, scaleY, opacity
discrete gate             visible
raw cycle phase           delay / iteration / direction
continuous interpolation  easing(raw phase)
transient composition     Rules -> overlay -> renderer
runtime immutability      no frame persistence / undo writes
```

M6.4.7 should explicitly settle:

- canonical visual target/property identity
- numeric vs discrete target semantics
- additive vs multiplicative vs gate composition
- relative/absolute authored intent where needed
- raw phase vs eased progress as separate runtime concepts
- generic overlay application independent of effect names
- stable IDs / future control handles
- the boundary between definition, activation/behavior and renderer
- backward-compatible mapping of current experiment definitions into the generic runtime

The first consolidation change should be small and testable: introduce generic visual target/composition descriptors and drive existing overlay application through them while retaining current `spin/move/scale/fade/blink` definitions as compatible authoring adapters. Do not begin with a destructive schema rewrite.

After the generic runtime path proves behavior-equivalent through the existing deterministic and deployed smoke suite, decide whether visual schema v4 is necessary for persistent generic definitions or whether the named definitions can remain authoring presets compiled into the generic runtime.

No additional named effect kinds should be added in M6.4.

## Deferred / non-goals

- arbitrary keyframe/timeline editor
- CSS animation import
- arbitrary cubic-bezier strings
- spring/physics simulation
- unrestricted script callbacks
- raw Konva Tween exposure
- Web Animations API as authored contract
- per-frame persistence
- SCADA-specific animation authoring
- a separate Pulse runtime primitive
