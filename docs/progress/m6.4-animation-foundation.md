# M6.4 Animation Foundation

Status: **architecture boundary defined; first model/evaluator slice next** on `main`.

M6.4 adds reusable private visual animation to Component Workbench without turning authored components into Konva/DOM programs.

## Goal

A component developer should be able to attach reusable animation behavior to a private visual Layer while SCADA Workbench continues to see only the component's public contract.

Initial animation families are expected to include:

```text
rotate / spin
blink
fade
pulse
move
scale
```

The first implementation slice does not need to expose every family in the editor. It must first prove the model and runtime boundary with one small animation primitive.

## Existing pipeline

Before M6.4, Component Preview resolves visual state as:

```text
serialized ComponentVisualDefinition
        ↓
resolveComponentVisualRules(visual, propertyValues)
        ↓
effective ComponentVisualDefinition
        ↓
CompositeComponentVisualRenderer
        ↓
Konva
```

Important existing properties:

- `ComponentVisualDefinition` is serializable private implementation data.
- Visual Rules target stable `layerId` values.
- Rules are pure model transformations driven by component Property values.
- `CompositeComponentVisualRenderer` consumes resolved Layer state and contains the Konva-specific rendering details.
- authored component logic receives no raw `Konva.Node`, React or DOM objects.

M6.4 must preserve those boundaries.

## Core decision: definitions are persistent; frames are transient

Animation definitions belong in the private serialized visual model.

Animation frames do **not**.

Do not update `ComponentVisualDefinition.layers` every animation frame and do not persist time-varying geometry/style back into the component package.

Target pipeline:

```text
serialized base Layer state
        ↓
Visual Rules
        ↓
effective rule-resolved Layer state
        ↓
Animation evaluator(time, properties, runtime activation)
        ↓
transient Animation Overlay
        ↓
compose effective Layer + overlay
        ↓
CompositeComponentVisualRenderer
        ↓
Konva
```

This gives animation a renderer-independent runtime boundary and keeps React/Konva as output adapters only.

## Why animation runs after Visual Rules

Visual Rules currently express property-driven effective base state, for example:

```text
running == true -> impeller.rotation = 20
alarm == true   -> indicator.opacity = 1
```

Animations should modulate the state produced by those rules rather than compete with rule persistence.

Example:

```text
base rotation = 0
Visual Rule    = 20 degrees
spin overlay   = +135 degrees at this frame
rendered       = 155 degrees
```

The rule still owns the effective base state; the animation owns only a transient delta/multiplier.

## Animation Overlay

The evaluator should return renderer-independent transient values keyed by stable Layer id rather than a mutated persisted visual document.

Conceptual shape:

```ts
type VisualAnimationOverlay = Record<string, {
  translateX?: number
  translateY?: number
  rotationDelta?: number
  scaleXMultiplier?: number
  scaleYMultiplier?: number
  opacityMultiplier?: number
  visible?: boolean
}>
```

Exact field naming may be refined during implementation, but the semantic rule is fixed:

- move is additive to resolved `x/y`
- rotate/spin is additive to resolved rotation
- scale/pulse is multiplicative with resolved `scaleX/scaleY`
- fade is multiplicative with resolved opacity
- blink may transiently control visibility

This makes common animations composable instead of introducing absolute-property races.

## Serialized animation definition

Animations are private component visual implementation data and target stable Layer ids, like Visual Rules.

The first model should use a discriminated union instead of a generic bag of arbitrary property names.

Conceptual common fields:

```ts
type VisualAnimationBase = {
  id: string
  enabled: boolean
  layerId: string
  timing: VisualAnimationTiming
  activation: VisualAnimationActivation
}
```

Timing foundation:

```ts
type VisualAnimationTiming = {
  durationMs: number
  delayMs: number
  iterations: number | 'infinite'
  direction: 'normal' | 'reverse' | 'alternate' | 'alternate-reverse'
  easing: 'linear' | 'ease-in' | 'ease-out' | 'ease-in-out'
}
```

Requirements:

- duration must be finite and greater than 0
- delay must be finite and non-negative
- finite iterations must be a positive integer
- no arbitrary CSS easing string or executable easing callback in the first slice

## Activation foundation

M6.4 should support two declarative activation modes first:

```text
always
property condition
```

Conceptual shape:

```ts
type VisualAnimationActivation =
  | { kind: 'always' }
  | {
      kind: 'property'
      propertyKey: string
      operator: VisualRuleOperator
      compareValue: ComponentScalarValue
    }
```

Property activation should reuse the same type/operator validation semantics as Visual Rules instead of inventing a second incompatible condition language.

Do not add Action/Event/script-triggered animation lifecycle in the first slice. M6.5 Controlled Script Runtime will need an explicit runtime animation-control API; the M6.4 model must leave room for that without pre-implementing it through browser globals.

## Initial animation family model

The complete family can converge incrementally. Expected semantic shapes:

```text
rotate/spin -> rotation delta over a cycle
move        -> x/y translation delta over a cycle
scale       -> x/y scale multipliers over a cycle
pulse       -> periodic scale multiplier
fade        -> opacity multiplier over a cycle
blink       -> periodic transient visibility
```

The first code slice should implement **spin/rotate only** end-to-end. This is enough to prove:

- serialization
- validation
- stable `layerId` target
- timing evaluation
- activation
- Preview clock
- Rules -> Animation -> Renderer composition
- no persistence of frame state

Only after this path is stable should editor authoring UI expand to the remaining families.

## Preview clock boundary

Animation evaluation needs time, but the pure evaluator must not read `Date.now()`, `performance.now()` or own `requestAnimationFrame` directly.

Target separation:

```text
React Preview host
  owns requestAnimationFrame / elapsed time
        ↓ passes timeMs
pure animation evaluator
        ↓
Animation Overlay
```

This keeps animation math deterministic and testable.

Design mode does not run animations. Preview mode owns the clock.

## Lifecycle semantics

For the first slice:

- entering Preview starts an animation epoch at `t = 0`
- leaving Preview stops the clock and discards transient overlays
- re-entering Preview starts again at `t = 0`
- changing preview Property values re-evaluates activation against the same Preview epoch
- inactive animation contributes no overlay
- no frame state is written into undo/redo history or package persistence

Later runtime publication can define a longer-lived component-instance clock, but Component Workbench Preview should stay deterministic and easy to reset.

## Multiple animations on one Layer

Composition must be deterministic.

Prefer semantic composition over last-write-wins:

```text
translation deltas       add
rotation deltas          add
scale multipliers        multiply
opacity multipliers      multiply
visibility overrides     deterministic boolean composition
```

The first spin-only slice avoids conflicting channels. Before adding fade + blink or scale + pulse together, tests must lock down their composition semantics.

## Model versioning

`ComponentVisualDefinition` is currently visual version 2 and already has a v1 -> v2 normalization path in component-library storage.

Adding serialized animation definitions should be treated as a real visual-schema evolution rather than silently changing the meaning of version 2.

Expected first implementation step:

```text
ComponentVisualDefinition v3
  + animations

storage parser
  v1 -> normalized v3
  v2 -> normalized v3 with animations: []
  v3 -> validate directly
```

Cloning, package save/load and rule/layer target reconciliation must preserve/reconcile animations as well as Rules.

## Layer identity reconciliation

Animations target stable `layerId` values.

Workbench layer operations must follow the same safety rule already used for Visual Rules:

- Layer id rename rewrites animation target id
- deleting the target Layer removes the orphaned animation
- grouping/ungrouping preserves animations targeting stable child ids
- deleting a Group removes animations that target that deleted Group along with other orphaned private implementation references

This reconciliation belongs in model/editor adapter code, not in Renderer.

## Renderer boundary

`CompositeComponentVisualRenderer` may receive already-composed effective visual state, or a resolved-layer view produced immediately before rendering.

It must **not**:

- parse animation definitions
- own authored animation timing semantics
- inspect public Property conditions
- expose Konva nodes as animation targets
- persist animated values

Renderer responsibility remains:

> draw the effective renderer-independent visual state it is given.

## Future Controlled Script Runtime compatibility

M6.5 should eventually be able to expose controlled operations such as conceptual:

```text
startAnimation(animationId)
stopAnimation(animationId)
restartAnimation(animationId)
```

That API should manipulate runtime activation/state by animation id. It must not return or accept `Konva.Node`/DOM/React objects.

M6.4 therefore uses stable animation ids and keeps authored definitions separate from transient runtime state.

## First implementation slice

M6.4.1 should be intentionally small:

1. bump visual schema to v3 and add a validated `animations` collection;
2. add v1/v2 -> v3 storage normalization;
3. define one `spin`/rotation animation variant plus common timing + activation types;
4. add pure timing/easing/activation evaluation that returns a Layer overlay;
5. add a pure composition helper applying the overlay after Visual Rules;
6. add deterministic unit tests for timing boundaries, looping/direction and property activation;
7. drive the evaluator from a Preview-only animation clock;
8. prove a spinning Layer in Component Preview without mutating persisted visual data;
9. add one browser smoke assertion only after the deterministic model tests are green.

No animation editor panel is required for the first slice; a minimal fixture/model path is preferable until the runtime boundary is proven.

## Non-goals for M6.4.1

- arbitrary keyframe editor
- CSS animation import
- arbitrary cubic-bezier strings
- spring/physics simulation
- timeline sequencing UI
- Action/Event-triggered animation orchestration
- unrestricted script callbacks
- raw Konva Tween exposure
- Web Animations API as authored component contract
- animation state persistence into ComponentVisualDefinition
- SCADA-specific animation configuration

## Acceptance gate for M6.4.1

M6.4.1 is acceptable when:

- existing v1/v2 component visuals still load through migration
- v3 animations validate and round-trip through package persistence
- invalid animation ids/layer targets/timing/property activation are rejected
- spin evaluation is deterministic for explicit `timeMs`
- Visual Rules resolve before animation overlay composition
- Component Preview visibly animates the Layer
- Design mode remains static and editable
- animation frames do not create undo history or dirty persisted geometry
- Renderer remains unaware of public Property condition logic and does not own animation timing semantics
- existing M6.3.4 deployed browser acceptance remains green
