# M6.4 Animation Foundation

Status: **M6.4.1 spin model/evaluator + M6.4.2 spin authoring UI accepted · 2026-08-26; M6.4 remains active** on `main`.

M6.4 adds reusable private visual animation to Component Workbench without turning authored components into Konva/DOM programs.

## Goal

A component developer should be able to attach reusable animation behavior to a private visual Layer while SCADA Workbench continues to see only the component's public contract.

Expected animation families remain:

```text
rotate / spin
blink
fade
pulse
move
scale
```

M6.4.1 proved the runtime/model boundary with `spin`; M6.4.2 exposes that accepted model through a real Layer Inspector authoring surface without changing the runtime boundary.

## Accepted runtime boundary

Before M6.4, Component Preview resolved visual state as:

```text
serialized ComponentVisualDefinition
        ↓
resolveComponentVisualRules(visual, propertyValues)
        ↓
effective ComponentVisualDefinition
        ↓
CompositeComponentVisualRenderer
        ↓
Konva
```

M6.4 extends that pipeline to:

```text
serialized base Layer state
        ↓
Visual Rules
        ↓
effective rule-resolved Layer state
        ↓
pure Animation Evaluator(timeMs, properties)
        ↓
transient Animation Overlay
        ↓
compose effective Layer + overlay
        ↓
CompositeComponentVisualRenderer
        ↓
Konva
```

The architectural rule is implemented and tested:

> Animation definitions are persistent; animation frames are transient.

Animation frames never update persisted `ComponentVisualDefinition.layers`, never create per-frame undo history and never expose raw `Konva.Node`, React or DOM objects as authored animation targets.

## Why animation runs after Visual Rules

Visual Rules own the effective base state. Animation only modulates that state transiently.

Example:

```text
serialized rotation = 0
Visual Rule         = 40 degrees
spin overlay        = +180 degrees
rendered rotation   = 220 degrees
```

The deterministic model test locks this ordering down explicitly.

## Serialized model

`ComponentVisualDefinition` was evolved from v2 to v3 and owns:

```ts
animations: readonly VisualAnimation[]
```

The first discriminated animation variant is:

```ts
type SpinVisualAnimation = {
  id: string
  kind: 'spin'
  enabled: boolean
  layerId: string
  degreesPerIteration: number
  timing: VisualAnimationTiming
  activation: VisualAnimationActivation
}
```

Timing foundation:

```ts
type VisualAnimationTiming = {
  durationMs: number
  delayMs: number
  iterations: number | 'infinite'
  direction: 'normal' | 'reverse' | 'alternate' | 'alternate-reverse'
  easing: 'linear' | 'ease-in' | 'ease-out' | 'ease-in-out'
}
```

Activation foundation:

```ts
type VisualAnimationActivation =
  | { kind: 'always' }
  | {
      kind: 'property'
      propertyKey: string
      operator: VisualRuleOperator
      compareValue: ComponentScalarValue
    }
```

Property activation deliberately reuses Visual Rule condition/operator semantics rather than introducing another expression language.

## Validation

`assertComponentVisualAnimations(definition, visual)` validates semantic animation references after the structural visual validator runs.

The accepted validation includes:

- unique, non-empty animation ids
- supported animation kind (`spin` currently)
- existing Layer targets
- finite `degreesPerIteration`
- positive finite duration
- non-negative finite delay
- positive integer finite iterations or `infinite`
- bounded direction/easing vocabulary
- existing Property references for conditional activation
- compare values compatible with Property type
- numeric-only relational operators

The Renderer performs none of this validation or condition evaluation.

## Pure evaluator and overlay

`src/component-system/animations.ts` is renderer-independent model code. It imports no React or Konva API.

The first overlay channel is:

```ts
type VisualAnimationLayerOverlay = {
  rotationDelta?: number
}
```

Spin overlays are additive. Multiple active spin definitions targeting one Layer add their rotation deltas deterministically.

Future families should preserve semantic composition instead of switching to last-write-wins:

```text
translation deltas       add
rotation deltas          add
scale multipliers        multiply
opacity multipliers      multiply
visibility overrides     deterministic boolean composition
```

Those channels should be added only when their first concrete family is implemented and tested.

## Preview clock boundary

Animation math receives explicit `timeMs`; it does not read clocks itself.

```text
Component Preview host
  owns requestAnimationFrame + elapsed epoch
        ↓
pure animation evaluator(timeMs)
        ↓
transient overlay
```

Implemented lifecycle:

- Design mode does not run animations
- entering Preview starts an epoch at `t = 0`
- leaving Preview stops the frame loop and clears transient time
- re-entering Preview starts from `t = 0` again
- Property changes re-evaluate activation against the current Preview epoch
- no animation frame invokes the package `onChange` path

## Visual schema migration

A dedicated pure helper owns stored visual normalization:

```text
v1 -> v3
  restore designSize from component default size
  animations: []

v2 -> v3
  preserve designSize/rules/layers
  animations: []

v3 -> validate directly
```

The migration itself is included in deterministic CI checks rather than being hidden only inside localStorage parsing.

## Reference reconciliation

Animations use stable ids and stable `layerId` references.

Workbench model operations preserve the same integrity expected from Visual Rules:

- Layer rename rewrites animation target ids
- Layer deletion removes orphaned target animations
- cloning a Layer subtree clones animations targeting that subtree and rewrites ids/targets
- grouping preserves child-targeted animations because child ids remain stable
- ungrouping removes an animation targeting the deleted Group wrapper while preserving child-targeted animations
- Property rename/delete reconciles Property-activated animations
- incompatible Property type/operator changes fall back to a safe valid condition shape rather than leaving invalid persisted data

This reconciliation remains outside the Renderer.

## Renderer boundary

`CompositeComponentVisualRenderer` still receives effective visual state and draws it.

It does **not**:

- parse animation definitions
- own authored timing semantics
- inspect Property activation conditions
- call `requestAnimationFrame`
- expose Konva nodes as authored animation targets
- persist animated values

This boundary is important for M6.5 Controlled Script Runtime, which can later operate on stable animation ids instead of renderer objects.

## M6.4.2 spin authoring UI

M6.4.2 exposes the accepted spin model as a first-class private Layer authoring capability.

Implemented:

- selected private Layer has an independent `动画` Inspector group, sibling to `视觉规则`
- list animations targeting the selected Layer
- add/remove `spin` animations
- enable/disable animation definitions
- edit degrees per iteration, including negative values
- edit duration and delay
- choose infinite or finite iterations and edit finite count
- edit direction: normal / reverse / alternate / alternate-reverse
- edit easing: linear / ease-in / ease-out / ease-in-out
- choose `always` or Property-condition activation
- Property activation reuses typed Visual Rule operator/value semantics
- default new spin is immediately previewable: `360° / 1000ms / infinite / normal / linear / always`
- all authoring edits update only the serialized animation definition; Preview still runs through the M6.4.1 pure evaluator

The animation editor is implemented in:

- `src/features/component-library/ComponentVisualAnimationEditor.tsx`
- `src/features/component-library/component-animation-editor.css`

The Layer Inspector owns the semantic grouping; `ComponentVisualRuleEditor` remains responsible only for Visual Rules.

## Next slice: M6.4.3 animation family expansion

The next slice should extend the renderer-independent animation model through the same accepted authoring/evaluator boundary rather than introduce a timeline system.

Candidate families remain:

```text
move
scale / pulse
fade
blink
```

Before implementing them, choose the smallest next family that proves one new overlay-composition channel and lock that channel down with deterministic tests. Do not add all families at once merely because the UI can host them.

The next slice should preserve these constraints:

- definitions remain serializable private component implementation
- runtime frames remain transient overlays
- Visual Rules resolve before animation overlays
- multiple animations compose semantically, not by renderer-specific last-write-wins
- authoring UI edits definitions only
- Renderer remains unaware of Property activation and authored timing semantics

## Future Controlled Script Runtime compatibility

M6.5 may later expose controlled runtime operations such as conceptual:

```text
startAnimation(animationId)
stopAnimation(animationId)
restartAnimation(animationId)
```

That API should manipulate runtime state by stable animation id. It must never return or accept `Konva.Node`, DOM or React objects.

## Deferred / non-goals

Still deferred from the animation foundation:

- arbitrary keyframe editor
- timeline sequencing UI
- CSS animation import
- arbitrary cubic-bezier strings
- spring/physics simulation
- Action/Event-triggered animation orchestration
- unrestricted script callbacks
- raw Konva Tween exposure
- Web Animations API as authored component contract
- animation frame persistence into `ComponentVisualDefinition`
- SCADA-specific animation authoring
