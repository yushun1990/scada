# M6.5.10 — Typed Action / Event contract and device action dispatch

Status: implementation complete · review gate

Date: 2026-08-28

## Goal

Turn Action/Event names into a usable public runtime contract before the new scene semantics are persisted long-term.

This gate closes the temporary ambiguity left by M6.5.9C:

- how DSL positional Action arguments reach a Component Action handler
- how Component Event payloads are shaped and validated
- how static DSL validation uses the same public contract
- how outbound Device/Platform Actions cross the host boundary without abusing inbound telemetry APIs

## Accepted contract direction

### Component Action

Action parameters are ordered scalar parameters.

```text
DSL ordered arguments
        ↓
compiled Action effect ordered arguments
        ↓
PreviewRuntime.invokeAction
        ↓
validated + frozen ordered argument array
        ↓
Component Action handler
```

The runtime does not silently map positional DSL arguments into an object.

Each parameter declares:

- `name`
- `title`
- scalar/select `kind`
- optional description
- explicit nullability
- select options when applicable
- trailing optionality

Required parameters may not appear after optional parameters.

### Component Event

Event payloads are shallow named scalar records.

A declared payload schema controls:

- required fields
- optional fields
- scalar/select type
- explicit nullability
- select options

Unknown fields are rejected.

An Event with no payload schema accepts no payload. This makes the absence of a payload contract meaningful instead of equivalent to `unknown`.

### Device / Platform Action dispatch

Inbound telemetry and outbound commands remain separate host capabilities.

```text
RuntimeDataSource
= inbound values

ScadaDeviceActionDispatcher
= outbound Device / Platform Action invocation
```

The compiled SCADA runtime still produces effects only. Preview converts a resolved interaction effect into a frozen `ScadaDeviceActionInvocation` and passes it to the dispatcher.

No network transport or product-specific RPC adapter is introduced by this gate.

## Delivered implementation

### Public component metadata

`src/component-system/definition.ts` adds:

- `ComponentContractValueDefinition`
- `ComponentActionParameterDefinition`
- `ComponentEventPayloadFieldDefinition`
- `ComponentActionArguments`
- `ComponentEventPayload`
- Action `parameters`
- Event `payload`
- shared contract scalar validation

### Definition validation

`src/component-system/validation.ts` now validates Action/Event contracts, including:

- malformed parameter/payload definitions
- duplicate Action parameter names
- required parameters after optional parameters
- select contracts without options
- invalid nullability/optional flags

### Runtime validation

`src/component-system/interactions.ts` provides deterministic normalization and validation for:

- Action argument count and values
- Event payload required/optional fields
- unknown Event payload fields
- payload-less Event enforcement

Normalized argument arrays and payload objects are frozen before user component code observes them.

### Runtime handler model

`ComponentActionHandler` now receives:

```ts
(context, argumentsValue: ComponentActionArguments)
```

instead of one untyped `unknown` input.

`ComponentActionHandlerContext.emit` accepts the typed scalar Event payload record.

### Static DSL validation

`src/scene/scada-dsl-analysis.ts` validates Action calls against the same public contract before runtime construction:

- minimum/maximum argument count
- each argument expression's static scalar type
- Component Actions
- primary-device Actions
- explicit external Actions

Dynamic select values are still runtime-validated against the declared option set. The static layer rejects incompatible scalar families and can be tightened further for literal option membership without changing the public model.

### Preview and device dispatch

`PreviewRuntime.invokeAction()` validates arguments before calling the component implementation.

`PreviewRuntime.emitEvent()` validates payloads before publishing the Event.

`src/runtime/device-action-dispatcher.ts` defines the explicit outbound host interface.

`attachPreviewScadaSemantics()` now:

- executes parameterized Component Actions rather than skipping them
- passes compiled ordered arguments directly through the validated Preview Action boundary
- forwards Interaction effects through `ScadaDeviceActionDispatcher`

The M6.5.9B settled Component Property invariant remains unchanged: Renderer and Action handlers still observe the same effective snapshot.

## Regression coverage

`check-typed-action-event-contract.ts` covers:

- valid Action/Event metadata
- duplicate Action parameter rejection
- optional-parameter ordering
- malformed Event payload schemas
- direct Preview Action arity/type/select validation
- frozen handler argument arrays
- direct Preview Event payload validation and freezing
- missing/unknown/wrong-type payload fields
- payload supplied to a payload-less Event
- DSL Action argument type mismatch
- DSL Action argument count mismatch
- parameterized compiled Component Action execution
- Renderer / Action settled snapshot identity
- typed Device Action invocation through the explicit dispatcher
- immutable device invocation/arguments

Existing DSL analysis and M6.5.9C Preview integration fixtures were updated to exercise the same contract rather than a compatibility-only callback.

## Boundary / non-goals

This gate does not add:

- Scene schema revision
- persisted Action/Event semantic model
- persisted DSL text
- Event payload references such as `event.*` inside DSL expressions
- Workbench contract-editing UI
- production device/RPC transport
- backend infrastructure
- unrestricted scripting

Stable IDs, canonical persisted references, schema migration and compatibility representation belong to **M6.5.11 Stable persistence semantics**.
