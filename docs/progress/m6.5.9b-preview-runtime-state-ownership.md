# M6.5.9B Preview Runtime State Ownership

## Status

Implementation complete on `feat/m6-5-9b-preview-state-ownership`; CI / review gate pending.

## Goal

Establish one host-owned effective Component Property model before the compiled SCADA DSL propagation runtime is connected to real Preview state.

M6.5.9B deliberately does not attach a DSL program to a Scene node yet. It defines the state and compatibility boundary that M6.5.9C will consume.

## Effective Component Property ownership

Preview now owns one immutable settled Component Property snapshot per component node.

The deterministic layer order is:

```text
Component definition defaults
        ↓
Authored Scene props
        ↓
Legacy Scene v6 runtime-value binding compatibility layer
        ↓
Compiled-DSL derived override layer
        ↓
One settled Component Property snapshot
        ├─ Renderer
        └─ Component Action handler context
```

`ComponentPropertyStore` is the single owner of this effective snapshot.

A derived update with `value: undefined` releases the compiled-derived override and falls back through the lower layers. Derived commits validate the public Component Property contract before publication.

## RuntimeValueStore boundary

`RuntimeValueStore` remains an external runtime-value store only.

It owns telemetry/mock/source scalar values such as:

```text
legacy.state = "alarm"
device.pressure = 0.42
```

It does not own effective component presentation state.

PreviewRuntime subscribes to RuntimeValueStore and refreshes the legacy Scene v6 binding compatibility layer inside `ComponentPropertyStore`. A later compiled DSL adapter must read external values from RuntimeValueStore but commit derived Component Property effects only through ComponentPropertyStore.

## Renderer / Component Action snapshot parity

Normal Preview rendering no longer reconstructs effective props independently from RuntimeValueStore.

`SceneNodeRenderer` subscribes to `PreviewRuntime.componentProps` and consumes the settled node snapshot.

`PreviewRuntime.invokeAction()` reads that exact same immutable snapshot and passes it as `ComponentActionHandlerContext.props`.

Therefore:

```text
Renderer props === Component Action handler props
```

for one committed Preview state, rather than merely relying on two callers to execute the same merge formula at approximately the same time.

The explicit `runtimeValues` renderer input remains as a fixture/compatibility path outside the normal PreviewRuntime-owned route.

## Legacy Scene v6 compatibility boundary

Scene v6 `bindings` and `behaviors` remain compatibility-only.

### Legacy bindings

Legacy `runtime-value` bindings remain active as a lower-priority compatibility layer. A compiled-derived override has deterministic precedence over a legacy binding targeting the same public Component Property.

This keeps existing Scene v6 documents functional without making the old binding representation the new semantic model.

### Legacy Event -> Component Action behaviors

PreviewRuntime now exposes `claimCompiledSemantics(nodeId)`.

Without a claim, legacy Scene v6 Event -> Component Action behavior dispatch continues unchanged.

While a component node has one or more compiled-semantics claims:

- Component Events are still emitted to runtime subscribers;
- legacy Scene v6 Event -> Component Action auto-dispatch is suppressed for that node;
- claims are reference-counted.

M6.5.9C must claim a node before attaching the new Interaction Binding event path. This prevents one Component Event from accidentally driving both the old Scene v6 behavior model and the new compiled Interaction model in parallel.

## Host sequencing contract for `componentPropertyChanged`

The M6.5.8 propagation-session method remains valid, but its host sequencing is now explicit.

When a non-DSL host-owned Component Property base value changes:

```text
1. Commit the new host/base value first.
2. Ensure readComponentBaseProperty(property) observes that new value.
3. Call propagationSession.componentPropertyChanged(property).
4. If propagation aborts, apply no derived Property or Action effects.
5. If propagation succeeds, commit the complete returned valueUpdates batch to
   ComponentPropertyStore before invoking any returned Component Action effects.
6. Component Actions then read the same settled ComponentPropertyStore snapshot
   that the Renderer observes.
```

For external source updates the analogous M6.5.9C order is:

```text
RuntimeValueStore source commit
        ↓
propagationSession.sourcePropertyChanged(...)
        ↓
atomic ComponentPropertyStore derived commit
        ↓
Component Action effects
```

The propagation session owns dependency evaluation and rollback. PreviewRuntime owns committed Component Property state and side-effect sequencing.

## Regression coverage

`scripts/check-preview-component-state.ts` covers:

- default -> authored -> legacy binding -> derived override ordering;
- RuntimeValueStore remaining distinct from Component Property state;
- external source changes not overriding an active compiled-derived value;
- explicit derived invalidation falling back to the current legacy value;
- derived update validation without corrupting committed state;
- Component Action handlers receiving the exact same immutable snapshot object exposed by ComponentPropertyStore;
- legacy Event -> Component Action behavior remaining active without a compiled claim;
- Component Events remaining visible while compiled claims suppress legacy behavior dispatch;
- reference-counted compiled claims;
- Preview stop clearing runtime-owned Component Property state.

## Boundary

This slice does not:

- compile or persist a DSL program on Scene nodes;
- call a propagation session from PreviewRuntime;
- dispatch Device/Platform Actions;
- change Scene schema version 6;
- extend legacy bindings/behaviors;
- add typed Action/Event payload schemas;
- introduce backend/runtime authority.

Those boundaries keep M6.5.9B focused on state ownership rather than broad Preview integration.
