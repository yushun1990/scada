# M6.7B3 Production deployment decision

Status: deployment decision recorded · defer deployment · gate acceptance pending deployed Pages smoke repair · 2026-08-29

## Decision

**Defer production publication-backend deployment.**

M6.7B2C removed the browser-authentication architecture blocker, but the current repository does not yet contain a production-ready frontend/API topology and operations contract. The publication service remains optional infrastructure; local Component Workbench editing, local user-component activation, installed remote cache hydration and SCADA runtime evaluation continue without it.

This decision is intentionally different from abandoning the backend. It keeps the production deployment workflow manual-only and records concrete reopening conditions.

The roadmap gate itself remains open until the post-#92 deployed Pages smoke is repaired and passes again. `PLAN.md` therefore stays authoritative with M6.7B3 as the current review gate in this PR.

## Evidence reviewed

### Frontend / API routing

The current GitHub Pages build sets only:

```text
VITE_BASE_PATH=/scada/
```

It does not currently set `VITE_PUBLICATION_API_URL`.

Therefore the deployed Pages application intentionally keeps remote publication disabled. Turning the variable on must follow, not precede, an accepted production API origin/topology.

### Cookie / domain topology

M6.7B2C uses an opaque HttpOnly publication session and `credentials: include`.

The historical deployment notes describe GitHub Pages in front of a separately hosted Nginx/API service, but no current production API hostname or same-site custom-domain arrangement is committed as product configuration.

A cross-site GitHub Pages -> unrelated API host deployment would require `SameSite=None; Secure` and would depend on third-party-cookie behavior. B3 does not accept that as the default production topology without an explicit browser smoke.

Preferred reopening direction:

```text
same-site/custom-domain frontend + API
```

or another topology whose credentialed browser behavior is explicitly verified in the supported browsers.

### Publisher identity and secrets

The current self-hosted publisher identity (`SCADA_PUBLISH_USERNAME` / `SCADA_PUBLISH_PASSWORD`) is accepted as the B2C session/identity boundary, but production still needs an explicit secret-generation and rotation procedure.

The historical deploy script currently generates only the PostgreSQL password and `SCADA_ADMIN_TOKEN`; it does not provision the B2C publisher credential or intentionally configure session cookie policy.

The administrator Bearer remains an operations/CI credential and must not become a browser credential.

### PostgreSQL lifecycle

The Quadlet PostgreSQL volume provides persistence, but the repository does not yet define production backup, restore verification or migration preflight/rollback procedures for the publication database.

A persistent volume alone is not a backup strategy.

### TLS / CORS / trusted Origin

The Fastify service has an accepted trusted-Origin boundary and CORS configuration, but the repository does not currently own a complete production TLS termination / API-host configuration. The historical system-Nginx topology is infrastructure evidence, not a current production contract.

### Observability and failure diagnostics

Current deployment assets can expose systemd/container status and the API has `/health`, but there is no accepted production monitoring/alerting or backup-failure diagnostic path.

This is acceptable while the backend is optional and undeployed; it is insufficient reason to make remote publication a production feature today.

## Post-merge Pages smoke finding

After PR #92 merged, GitHub Pages deployment succeeded, but the generic Pages Browser Smoke failed before reaching any B2C publication flow.

The failure was a stale test fixture: `scripts/pages-smoke.mjs` still read and wrote the legacy `scada-editor-lab.components.v2` localStorage key even though M6.6 made IndexedDB the normal persistence authority.

This branch repairs the smoke fixture to use the current IndexedDB `components` store and waits for asynchronous Save completion. The fix does **not** restore localStorage as an active storage path.

Because this is a deployed-browser verification requirement, B3 is not marked accepted in `PLAN.md` until the repaired script has been merged, run against the deployed Pages revision and passed.

This failure reinforces the repository policy that deployed-browser evidence must follow persistence/runtime architecture rather than bypass it.

## Reopening conditions for production deployment

Production publication deployment may be reconsidered only when all of the following are intentionally addressed:

1. choose and record the production frontend URL and publication API URL
2. choose same-site/custom-domain or explicitly accept/test a cross-site cookie topology
3. provide `VITE_PUBLICATION_API_URL` through the frontend deployment configuration only after the API origin is accepted
4. provision browser publisher credentials separately from `SCADA_ADMIN_TOKEN`, with a rotation procedure
5. make cookie `Secure` / `SameSite` configuration explicit for the chosen topology
6. define PostgreSQL migration preflight, backup, restore verification and rollback expectations
7. define TLS termination, trusted Origin and CORS values as production configuration
8. define minimum health/logging/failure diagnostics for the publication service and database
9. run end-to-end browser verification:

```text
Login
  -> explicit Publish
  -> public retrieval
  -> explicit install
  -> local/offline cache
  -> offline Scene activation
```

10. only after that verification, record a new explicit **deploy now** decision before enabling automatic backend deployment

## Workflow policy after this decision

`deploy-backend.yml` remains `workflow_dispatch` only.

Do not re-add a `push` trigger while the B3 decision is `defer deployment`.

Manual workflow availability is retained as infrastructure evidence/testing capability; it is not authorization to treat the current assets as an accepted production deployment.

## Roadmap consequence after smoke acceptance

Once the repaired deployed Pages smoke passes, M6.7B3 can be closed with the recorded **defer deployment** decision.

At that point M6.7B is accepted through the client publication/retrieval boundary, remote production infrastructure remains gated by the reopening conditions above, and the main roadmap can advance to M7 packaging / production-adapter preparation / reusable component set without making the backend a prerequisite for local editing or runtime evaluation.
