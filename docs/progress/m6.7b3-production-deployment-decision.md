# M6.7B3 Production deployment decision

Status: accepted review gate · defer deployment · 2026-08-30

## Decision

**Defer production publication-backend deployment.**

M6.7B2C removed the browser-authentication architecture blocker, but the repository still does not own an accepted production frontend/API topology and operations contract. The publication service remains optional infrastructure; local Component Workbench editing, local user-component activation, installed remote cache hydration and SCADA runtime evaluation continue without it.

This decision does not abandon the backend. It keeps production deployment gated while allowing the main product roadmap to advance to M7.

## Evidence reviewed

### Frontend / API routing

The current GitHub Pages build sets `VITE_BASE_PATH=/scada/` and does not set `VITE_PUBLICATION_API_URL`. Remote publication therefore remains intentionally disabled on the public Pages build until a production API origin/topology is accepted.

### Cookie / domain topology

M6.7B2C uses an opaque HttpOnly publication session and `credentials: include`.

No production API hostname or same-site custom-domain arrangement is currently committed as product configuration. A GitHub Pages -> unrelated API-host deployment would require explicit cross-site-cookie behavior and browser verification; third-party-cookie availability must not be assumed.

Preferred reopening direction is a same-site/custom-domain frontend + API topology, or another topology whose credentialed browser behavior is explicitly verified.

### Publisher identity and secrets

The current self-hosted publisher identity (`SCADA_PUBLISH_USERNAME` / `SCADA_PUBLISH_PASSWORD`) is sufficient to establish the B2C session/identity boundary, but production still needs explicit secret generation and rotation.

`SCADA_ADMIN_TOKEN` remains a server/CI operations credential and must not become a browser credential.

### PostgreSQL lifecycle

The Quadlet PostgreSQL volume provides persistence but is not a backup strategy. Production still requires migration preflight, backup, restore verification and rollback expectations.

### TLS / CORS / trusted Origin

The Fastify service has accepted trusted-Origin semantics, but the repository does not yet own a complete production TLS termination/API-host configuration.

### Observability and failure diagnostics

The current assets expose basic health/container information but no accepted production monitoring/alerting or backup-failure diagnostic path.

## Deployed browser verification

The initial post-B2C Pages verification exposed stale test fixtures that still bypassed the M6.6 IndexedDB persistence authority. Those fixtures were repaired in successive narrow PRs:

- #93 migrated the primary Component Editor Pages fixture to IndexedDB
- #94 migrated Move / Scale / Fade / Blink animation fixtures to the shared IndexedDB component fixture path
- #95 migrated the final SCADA geometry Scene fixture to the IndexedDB `scenes` store and waited for real async Save persistence

After #95 merged at `main@4aabf74d2cb14c3fa1fc466fec4e3c28c1e2ffee`:

- GitHub Pages deployment succeeded
- `Pages Browser Smoke` run #179 (`33287223003`) completed successfully
- job `99192405823` passed the complete deployed-browser suite, including the final SCADA geometry stage

This closes the B3 verification gate. The result authorizes **defer deployment**, not production provisioning.

## Reopening conditions for production deployment

Production publication deployment may be reconsidered only when all of the following are intentionally addressed:

1. choose and record the production frontend URL and publication API URL
2. choose same-site/custom-domain or explicitly accept/test a cross-site cookie topology
3. provide `VITE_PUBLICATION_API_URL` only after the API origin is accepted
4. provision browser publisher credentials separately from `SCADA_ADMIN_TOKEN`, with a rotation procedure
5. make cookie `Secure` / `SameSite` policy explicit for the chosen topology
6. define PostgreSQL migration preflight, backup, restore verification and rollback expectations
7. define TLS termination, trusted Origin and CORS values as production configuration
8. define minimum health/logging/failure diagnostics for the publication service and database
9. run end-to-end browser verification:

```text
Login
  -> explicit Publish
  -> public retrieval
  -> explicit install
  -> local/offline cache
  -> offline Scene activation
```

10. record a new explicit **deploy now** decision before enabling automatic backend deployment

## Workflow policy

`deploy-backend.yml` remains `workflow_dispatch` only.

Do not restore automatic deployment while the accepted B3 decision is `defer deployment`.

Manual workflow availability remains infrastructure evidence/testing capability, not authorization to treat the current assets as an accepted production deployment.

## Roadmap consequence

M6.7B is accepted through the client publication/retrieval/install boundary. M6 is closed as the accepted Component Workbench + scene-semantics baseline.

The main roadmap advances to M7 without making the publication backend a prerequisite for local editing or runtime evaluation.
