# M6.5.5 SCADA DSL Semantic Lowering

Status: **Value / Behavior / Interaction semantic lowering accepted; persistence and editor UI remain deferred**.

This slice follows `m6.5.4-scada-dsl-surface.md`. The DSL remains an authoring/interaction surface. This slice proves that readable source can lower into structured runtime concepts without making DSL text the persistence model or turning SCADA into a general rule engine.

---

## 1. Accepted semantic split

The three ordinary authoring forms now map to three separate semantic plans:

```text
component.property = expression
        ↓
Value Binding

if condition {
  component.action()
}
        ↓
Behavior Binding

on component.event {
  device.action()
}
        ↓
Interaction Binding
```

The separation is intentional:

- Value Binding represents reconstructible current UI state and is declarative/pure.
- Behavior Binding represents data-driven **component-local** transient behavior.
- Interaction Binding is the only first-slice path from a Component Event to a device/platform side effect.

A data condition is deliberately not allowed to invoke a device Action directly.

## 3. Value Binding semantics

Example:

```text
component.state =
  if device.fault then "fault"
  else if device.running then "running"
  else "stopped"

component.level = outlet.pressure * 100
```

Lowering produces a structured target Property plus a pure semantic expression tree.

Important boundaries:

- assignment target must be a current Component Property;
- `device.*` lowers to a structured `primary-device` reference rather than the concrete device selected while authoring;
- explicit sources such as `outlet.*` lower to stable external source IDs;
- Property assignment inside a Behavior `if` block is rejected. Persistent/reconstructible UI truth must use declarative Value Binding instead of imperative mutation.

The expression evaluator currently supports the accepted scalar arithmetic/comparison/boolean/conditional subset and returns an invalid/undefined result for missing values, type-invalid operations, division/modulo by zero, or non-finite numeric output.

## 4. Behavior Binding semantics

Example:

```text
if device.fault and outlet.pressure > 1.2 {
  component.showFault()
}
else if device.running {
  component.showRunning()
}
else {
  component.showStopped()
}
```

### Ordered branches are semantic, not cosmetic

This slice deliberately does **not** force DSL `if / else if / else` into the earlier flat AND-within / OR-across exploratory condition-group contract.

Doing so would either:

- lose `else-if` priority; or
- require arbitrary expressions to be expanded into DNF-like condition groups.

Instead the semantic plan preserves an ordered branch list. The first branch whose expression evaluates to `true` becomes active; a final `else` is represented as the fallback branch.

### Branch-entry Action semantics

Component Actions inside a Behavior use **branch-entry** semantics:

```text
no branch → fault branch     => fire showFault() once
fault branch → fault branch  => do not replay
fault branch → running       => fire showRunning() once
running → else               => fire showStopped() once
```

Repeated telemetry that changes values but leaves the same ordered branch active does not replay one-shot Component Actions.

If an `if` has no `else`, leaving its last matched branch and reaching no branch performs no implicit Action.

This keeps a useful distinction:

```text
Property = what the component is now
Action   = something the component should do on entering a behavior state
```

### Device automation remains outside Behavior

This is rejected:

```text
if device.fault {
  device.stop()
}
```

SCADA presentation conditions must not silently become device-to-device/process automation.

## 5. Interaction Binding semantics

The DSL now includes the intentionally narrow explicit interaction form:

```text
on component.startRequested {
  device.start()
}
```

or an explicit external target:

```text
on component.stopRequested {
  valve.close()
}
```

Lowering rules:

- `on` source must be a current Component Event;
- target must be a primary-device or explicit external-device Action;
- `device.action()` lowers to a copy/rebind-safe `primary-device` Action reference;
- external targets preserve stable external source IDs;
- Action arguments are lowered as pure expressions for evaluation when the Event occurs;
- first slice permits exactly **one** device Action per `on` block.

The one-Action restriction is deliberate: this slice does not introduce sequencing, workflow, retry, or orchestration semantics. Multiple-action behavior should only be added later if a concrete SCADA interaction use case proves it necessary.

A Component Action is also not treated as a device-side Interaction target in this first slice; data-driven Component Actions remain Behavior semantics.

---

## 6. Primary-device copy/rebind semantics

A critical acceptance property is that readable DSL such as:

```text
device.fault
device.start()
```

must not capture the concrete device ID selected during authoring.

The semantic plan stores:

```text
scope: primary-device
property/action: <capability>
```

Therefore:

```text
copy configured component
        ↓
change Pump01 → Pump02
        ↓
all device.* Property/Action references resolve against Pump02
```

without rewriting DSL/semantic branches.

Explicit references such as `outlet.*` or `valve.*` remain stable external references and do not silently change when the primary device is rebound.

## 8. Intentionally unresolved

Do not treat this slice as persistence/schema or editor syntax freeze. Still unresolved:

1. semantic type checking beyond runtime evaluator guards;
2. Action parameter schemas — current `ComponentActionDefinition` still only exposes title/description;
3. stable persisted IDs independent of statement position;
4. incremental/error-tolerant parsing for partially typed editor text;
5. dependency extraction and selective reevaluation;
6. runtime session integration for applying Value Bindings and tracking active Behavior branches;
7. persistence/schema versioning;
8. final braces-vs-indentation presentation;
9. actual LSP-like completion/tag editor UI;
10. whether an Interaction ever needs more than one independent device Action.

QuickJS remains unrelated to this core path and should stay paused unless a later advanced escape-hatch requirement cannot be expressed by the structured model.

## 9. Next checkpoint

The next useful slice should validate **types and dependencies before persistence/UI**:

```text
DSL semantic expression
   ↓
static result type + dependency set
   ↓
validate target Property / condition / Action args
```

At minimum:

- Behavior conditions must statically resolve to boolean-compatible expressions;
- arithmetic/comparison operands should be validated from capability metadata;
- Value Binding result must be compatible with the target Component Property;
- referenced source dependencies should be extractable for selective reevaluation;
- Action arguments should remain deferred until the public Action contract has a parameter schema rather than inventing ad-hoc positional types in the DSL layer.
