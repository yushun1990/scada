# M6.5 Controlled Script / Component Behavior Runtime

Status: **behavior-model consolidation active; first SCADA Behavior Binding contract slice accepted; production QuickJS adapter intentionally paused**.

M6.5 began by building a safe component-private execution boundary on top of the accepted M6.4 Visual Runtime. The low-level safety work remains useful, but product discussion exposed an important architectural correction: SCADA dynamics should not be centered on imperative scripting.

The current design direction is recorded in:

- `docs/architecture/scada-binding-behavior.md`

The main question is now broader than "how do we safely execute JavaScript?":

> **What is the smallest understandable component behavior model that lets normal SCADA authors map data and interactions to a component's public Properties / Actions / Events without turning SCADA into a rule engine?**

---

## Architectural direction

The scene-level model under consolidation is:

```text
Value Binding
  multiple runtime values
      ↓
  pure expression
      ↓
  Component Property

Behavior Binding
  local data transition / condition
      ↓
  Component Action
      ↓
  component-private transient behavior

Interaction Binding
  user / Component Event
      ↓
  Device / Platform Action
```

A reusable component continues to expose the accepted public contract:

```text
Properties
Actions
Events
Anchors
```

Complex visual work should normally be encapsulated behind Component Properties/Actions rather than configured against private layers in the SCADA Workbench.

The SCADA layer may derive sophisticated presentation state from multiple points, but it must not silently become a general device automation/rule engine. Process sequencing, device-to-device orchestration, business state machines, retry/timer workflows, and platform-level virtual values belong outside ordinary SCADA scene behavior.

The ordinary authoring UI should therefore be structured **condition groups + Action** configuration plus value bindings, not a blank script editor.

A key reuse direction is:

> **One component instance commonly represents one primary device instance.**

Most references can then be relative to a primary device context. Copying a configured component can preserve all bindings/conditions/actions and normally require only changing the primary device, with structured stable references resolving against the new device contract.

## SCADA Behavior Binding contract — first model slice accepted

Implementation:

- `src/scene/scada-behavior-contract.ts`
- `scripts/check-scada-behavior-contract.ts`

This first slice intentionally remains independent from persisted `SceneDocument` v6. It does **not** introduce Scene v7 yet. The goal is to prove the semantics before paying a schema migration/UI cost.

### Condition model

The ordinary authoring model is deliberately flat:

```text
Group A
  condition 1
  AND condition 2

OR

Group B
  condition 3
  AND condition 4
```

Contract semantics:

```text
AND within one condition group
OR across condition groups
```

This avoids exposing arbitrary nested Boolean expression trees to ordinary scene authors while still covering the intended multi-condition SCADA presentation cases.

### Reference model

A runtime Property reference is either:

```text
primary-device relative reference
external explicit reference
```

Conceptually:

```text
${device.running}
${device.fault}

vs.

${external-pressure-sensor.pressure}
```

Changing the component's primary device therefore re-resolves all relative references without rewriting the Behavior definition. Explicit external references remain unchanged.

The same relative/external distinction is defined for device Action targets used by Interaction Bindings.

A missing primary device never resolves silently; primary-device references remain unresolved until a device context exists.

### Behavior edge semantics

A Behavior Binding invokes a **Component Action**, not an arbitrary device Action.

The first slice supports explicit transition semantics:

```text
enter: condition false -> true
leave: condition true -> false
```

This prevents repeated equal telemetry from replaying a one-shot component behavior on every update.

Example:

```text
fault = true every second
```

must not repeatedly invoke:

```text
component.enterFault()
```

once the condition is already matched.

### Accepted boundary

The first contract therefore fixes these principles:

- ordinary Behavior conditions may combine multiple values;
- Behavior side effects remain narrow: **condition transition -> Component Action**;
- primary-device references are relative and rebind by changing device context;
- external references remain explicit escape hatches;
- Interaction Binding device Actions use the same primary/external reference model;
- repeated telemetry does not replay one-shot component Actions;
- no timers, retries, process sequencing, device-to-device automation, arbitrary script, or renderer access enters this SCADA Behavior slice.

## M6.5.1 Controlled Runtime capability contract — completed foundation

Implementation:

- `src/component-system/controlledRuntime.ts`

The capability facade established bounded, renderer-independent host operations:

```text
runtime.properties
  get / set / clear

runtime.events
  emit

runtime.actions
  invoke

runtime.visual
  set / clear
  contribute / clearContribution

runtime.diagnostics
  log
```

Important accepted properties of this foundation:

- Property/Event/Action names are validated against the component public definition.
- Visual Layer IDs and canonical M6.4 targets are validated.
- Runtime overrides remain separate from authored state.
- Absolute visual values and composable contributions are separate.
- Contributions use stable `controlId` slots instead of unbounded accumulation.
- No DOM/React/Konva/browser globals are part of the contract.

Acceptance revision:

`3dd13007da11389b8b8478652851e935f8a649e3`

- CI #551 ✅
- Pages Deploy #144 ✅

This API is no longer assumed to be the final **user-script** API. Some or all of it may become an internal host/effect executor behind the Component Behavior Runtime.

Implementation:

- `src/component-system/visualRuntimeState.ts`
- `src/runtime/controlled-runtime-session.ts`
- `scripts/check-controlled-runtime-session.ts`

The session proves runtime-only state can be owned outside authored component/scene state:

- dynamic base Property values;
- reversible Property overrides;
- reversible absolute visual values;
- stable contribution slots keyed by `controlId`;
- M6.4 `add / multiply / gate` composition;
- bounded Event/Action/Diagnostics host callbacks;
- deterministic reset/dispose lifecycle.

Important semantic check:

> Clearing an override restores the **current** base/rule-resolved value, not a stale value captured when the override was created.

## M6.5.3A Serializable sandbox protocol — accepted foundation

Implementation:

- `src/runtime/controlled-script-protocol.ts`
- `scripts/check-controlled-script-protocol.ts`

The protocol defines finite JSON-compatible values and a validated bridge from sandbox messages to declared Controlled Runtime capabilities.

It rejects unsupported/cyclic/prototype-rich values and preserves synchronous fast paths for Property/Visual/Event/Diagnostics operations while allowing Action invocation to be asynchronous.

## QuickJS dependency experiment — retained, adapter paused

The repository currently includes the minimal browser/WASM QuickJS dependency pair:

```text
quickjs-emscripten-core 0.32.0
@jitl/quickjs-wasmfile-release-sync 0.32.0
```

The lockfile was regenerated through npm and the temporary lock-sync workflow was removed afterward.

QuickJS remains a plausible implementation engine for a future advanced sandbox, but it is explicitly **not** the SCADA product model and must not dictate the public component behavior API.

Do not continue the production QuickJS adapter until the Component Behavior model is reconciled with:

- Value / Behavior / Interaction Bindings;
- Component Property / Action / Event semantics;
- transient runtime state;
- explicit host Effects;
- primary device context and copy/rebind behavior;
- the accepted M6.4 Visual Runtime.

## Next architecture / implementation checkpoint

The first Behavior model slice is now proven independently. The next work should stay incremental and avoid a premature Scene v7 migration.

Remaining checkpoints:

1. define the pure **Value Binding expression contract** for multiple inputs -> one Component Property;
2. map Component Action invocation into an internal Message/Update/transient-state boundary rather than direct private-Layer mutation;
3. define Interaction Binding Action inputs once the public `ActionDefinition` parameter schema is settled;
4. decide when the three proven binding families are stable enough to enter `SceneDocument`, and only then introduce a schema version/migration if required;
5. persist primary-device context on component instances and implement copy/duplicate -> change device -> automatic relative-reference rebind;
6. validate primary-device compatibility against the available Property/Action/Event contract and surface only missing/incompatible capabilities;
7. define explicit permitted Effects and their host executor;
8. decide which existing Controlled Runtime operations remain host internals rather than user-facing APIs;
9. wire the existing sandbox codec check into CI if the advanced-script path remains relevant;
10. decide whether SCADA v1 needs advanced script at all, and if so keep its role compute/update-oriented rather than imperative runtime mutation.

Until these checkpoints settle, M6.5 remains a **Component Behavior architecture and runtime convergence phase**, not a race to finish a JavaScript sandbox.
