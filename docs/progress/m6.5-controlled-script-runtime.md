# M6.5 Controlled Script / Component Behavior Runtime

Status: **behavior-model review active; production QuickJS adapter intentionally paused**.

M6.5 began by building a safe component-private execution boundary on top of the accepted M6.4 Visual Runtime. The low-level safety work remains useful, but product discussion exposed an important architectural correction: SCADA dynamics should not be centered on imperative scripting.

The current design direction is recorded in:

- `docs/architecture/scada-binding-behavior.md`

The main question is now broader than "how do we safely execute JavaScript?":

> **What is the smallest understandable component behavior model that lets normal SCADA authors map data and interactions to a component's public Properties / Actions / Events without turning SCADA into a rule engine?**

---

## Architectural direction under review

The emerging scene-level model is:

```text
Value Binding
  multiple runtime values
      ↓
  pure expression
      ↓
  Component Property

Behavior Binding
  local data transition / condition
      ↓
  Component Action
      ↓
  component-private transient behavior

Interaction Binding
  user / Component Event
      ↓
  Device / Platform Action
```

A reusable component continues to expose the accepted public contract:

```text
Properties
Actions
Events
Anchors
```

Complex visual work should normally be encapsulated behind Component Properties/Actions rather than configured against private layers in the SCADA Workbench.

The SCADA layer may derive sophisticated presentation state from multiple points, but it must not silently become a general device automation/rule engine. Process sequencing, device-to-device orchestration, business state machines, retry/timer workflows, and platform-level virtual values belong outside ordinary SCADA scene behavior.

The likely ordinary authoring UI is therefore structured **condition group + Action** configuration plus value bindings, not a blank script editor.

A key reuse direction is also under evaluation:

> **One component instance commonly represents one primary device instance.**

Most references can then be relative to a primary device context. Copying a configured component can preserve all bindings/conditions/actions and normally require only changing the primary device, with structured stable references resolving against the new device contract.

## M6.5.1 Controlled Runtime capability contract — completed foundation

Implementation:

- `src/component-system/controlledRuntime.ts`

The capability facade established bounded, renderer-independent host operations:

```text
runtime.properties
  get / set / clear

runtime.events
  emit

runtime.actions
  invoke

runtime.visual
  set / clear
  contribute / clearContribution

runtime.diagnostics
  log
```

Important accepted properties of this foundation:

- Property/Event/Action names are validated against the component public definition.
- Visual Layer IDs and canonical M6.4 targets are validated.
- Runtime overrides remain separate from authored state.
- Absolute visual values and composable contributions are separate.
- Contributions use stable `controlId` slots instead of unbounded accumulation.
- No DOM/React/Konva/browser globals are part of the contract.

Acceptance revision:

`3dd13007da11389b8b8478652851e935f8a649e3`

- CI #551 ✅
- Pages Deploy #144 ✅

This API is no longer assumed to be the final **user-script** API. Some or all of it may become an internal host/effect executor behind the Component Behavior Runtime.

## M6.5.2 Host-owned Controlled Runtime session — accepted

Implementation:

- `src/component-system/visualRuntimeState.ts`
- `src/runtime/controlled-runtime-session.ts`
- `scripts/check-controlled-runtime-session.ts`

The session proves runtime-only state can be owned outside authored component/scene state:

- dynamic base Property values;
- reversible Property overrides;
- reversible absolute visual values;
- stable contribution slots keyed by `controlId`;
- M6.4 `add / multiply / gate` composition;
- bounded Event/Action/Diagnostics host callbacks;
- deterministic reset/dispose lifecycle.

Important semantic check:

> Clearing an override restores the **current** base/rule-resolved value, not a stale value captured when the override was created.

Acceptance revision:

`5f73313ca1e1c28caccb93292c245c285dcebfdf`

This host-owned state model remains useful regardless of whether advanced script survives as a first-class authoring mechanism.

## M6.5.3A Serializable sandbox protocol — accepted foundation

Implementation:

- `src/runtime/controlled-script-protocol.ts`
- `scripts/check-controlled-script-protocol.ts`

The protocol defines finite JSON-compatible values and a validated bridge from sandbox messages to declared Controlled Runtime capabilities.

It rejects unsupported/cyclic/prototype-rich values and preserves synchronous fast paths for Property/Visual/Event/Diagnostics operations while allowing Action invocation to be asynchronous.

## M6.5.3B Engine-neutral execution contract — model accepted

Implementation:

- `src/runtime/controlled-script-engine.ts`
- `scripts/check-controlled-script-engine-contract.ts`

The engine abstraction deliberately avoids leaking a concrete JavaScript engine into the component/runtime architecture.

Current first-slice invocation lifecycle:

```text
init
propertyChanged
action
dispose
```

and bounded execution-limit fields currently include CPU timeout, memory, and stack limits.

CI-wired revision:

`fcf43ca0bb18c648fa0a3e89a300926dad6ae73d`

- CI #567 ✅

Before a concrete QuickJS adapter is implemented, the execution-limit contract still needs refinement if this path remains necessary, especially separating VM CPU budget from asynchronous host-call timeout and bounding host calls per invocation.

The codec validates raw sandbox JSON before it can reach the capability bridge, including call kind, required fields, canonical Visual targets, diagnostic levels, value shape, and message-size bounds.

## QuickJS dependency experiment — retained, adapter paused

The repository currently includes the minimal browser/WASM QuickJS dependency pair:

```text
quickjs-emscripten-core 0.32.0
@jitl/quickjs-wasmfile-release-sync 0.32.0
```

The lockfile was regenerated through npm and the temporary lock-sync workflow was removed afterward.

QuickJS remains a plausible implementation engine for a future advanced sandbox, but it is explicitly **not** the SCADA product model and must not dictate the public component behavior API.

Do not continue the production QuickJS adapter until the Component Behavior model is reconciled with:

- Value / Behavior / Interaction Bindings;
- Component Property / Action / Event semantics;
- transient runtime state;
- explicit host Effects;
- primary device context and copy/rebind behavior;
- the accepted M6.4 Visual Runtime.

---

## Next architecture checkpoint

Before further sandbox implementation, settle:

1. persisted Value Binding shape;
2. persisted Behavior Binding shape for multiple condition groups + Component Action;
3. persisted Interaction Binding shape for Component/User Event → external Action;
4. transition semantics so repeated equal telemetry does not replay one-shot actions;
5. Component Action → internal Message/Update/transient-state boundary;
6. explicit permitted Effects and their host executor;
7. primary-device relative references and external-reference escape hatch;
8. copy/duplicate/rebind semantics;
9. which existing Controlled Runtime operations remain internal implementation APIs;
10. whether SCADA v1 needs advanced script at all, and if so whether its role is pure compute/update rather than imperative runtime mutation.

Until this review is complete, M6.5 should be treated as a **behavior architecture checkpoint**, not as a race to finish a JavaScript sandbox.
