# M6.5 Controlled Script Runtime

Status: **M6.5.1 Controlled Runtime capability contract is active** on `main`.

M6.4 proved and consolidated the renderer-independent Visual Runtime. M6.5 now builds a deliberately small component-private execution boundary on top of that model.

## Goal

A Workbench-authored component may eventually execute controlled behavior/script logic without receiving unrestricted browser or renderer objects.

The intended boundary is:

```text
Component-private Behavior / Script
        ↓
Controlled Component Runtime
        ├─ Property API
        ├─ Event / Action API
        ├─ Visual API
        └─ Diagnostics
        ↓
Host-owned runtime state
        ↓
Visual Runtime / scene runtime
        ↓
Renderer
```

The script-facing surface must never automatically expose:

```text
window
document
React
Konva.Node
eval / Function
arbitrary imports
unrestricted network clients
```

External protocols remain behind runtime/data-source abstractions.

## M6.5.1 Controlled Runtime capability contract — active

First implementation lives in `src/component-system/controlledRuntime.ts`.

The facade is capability-only:

```text
runtime.properties
  get(key)
  set(key, value)       // runtime override; not authored scene/package state
  clear(key)            // restore host/base value

runtime.events
  emit(event, payload?)

runtime.actions
  invoke(action, input?)

runtime.visual
  set(layer, target, value)                    // absolute runtime value
  clear(layer, target)
  contribute(controlId, layer, target, value)  // transient composable contribution
  clearContribution(controlId)

runtime.diagnostics
  log(level, message, details?)
```

### Contract rules

- Property/Event/Action names must exist in the component public definition.
- Property writes are type-checked against `ComponentPropertyDefinition`.
- Visual Layer IDs must exist in the private visual definition.
- Visual targets are the canonical M6.4.7 Visual Runtime targets, not renderer node properties.
- Absolute visual writes and composable contributions are intentionally separate concepts.
- Property and absolute visual overrides are explicitly reversible.
- Contributions require a stable `controlId`; repeated execution updates the same control slot instead of accidentally accumulating unbounded deltas/multipliers.
- Scale contributions remain positive; absolute scale may be negative for mirroring but never zero.
- Opacity absolute/contribution values remain bounded to `0..1` in this first controlled API.
- Visibility contribution is a boolean gate and therefore cannot force hidden base/rule state visible.
- Diagnostics are host-routed and do not imply console/global access.

## Next: M6.5.2 Host-owned runtime session

Implement a renderer-independent host/session that owns runtime-only state:

```text
base/effective Property values
        ↓
component runtime Property overrides

rule-resolved visual state
        ↓
absolute runtime visual overrides
        ↓
animation + controlled contribution overlays
        ↓
renderer
```

It must prove:

- runtime Property overrides do not rewrite authored component/scene props;
- `clear` restores current base/bound value rather than a stale copy;
- absolute Visual values are host-owned and reversible;
- contribution `controlId` is an idempotent slot, not an accumulating command;
- multiple control slots compose through the M6.4.7 `add / multiply / gate` rules;
- Preview lifecycle disposal clears all controlled state;
- Event/Action callbacks remain bounded host capabilities;
- Diagnostics are retained/routed by the host;
- no DOM/React/Konva dependency enters the controlled runtime model.

Do not choose a scripting language or execute `implementationDraft` until this host state/lifecycle contract is accepted.
