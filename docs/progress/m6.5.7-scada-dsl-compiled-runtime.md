# M6.5.7 — SCADA DSL compiled runtime index

Status: accepted implementation checkpoint.

## Scope

This slice turns the static dependency graph from M6.5.6 into a runtime-only reverse index. It does **not** add UI, persistence, a new Scene schema version, QuickJS execution, or direct device/renderer access.

The authored DSL still lowers to structured Value / Behavior / Interaction plans. `compileScadaDslRuntime()` derives an ephemeral index from that semantic plan.

## Runtime routing

A concrete source update is routed only to plans whose **trigger dependencies** match the changed source/property.

For the primary device, the compiled index keeps relative references such as:

```text
device.fault
```

as a primary-device property dependency. The concrete `deviceId` is supplied only when an update is routed. Therefore copying/rebinding a component does not rewrite DSL and does not require a different persisted plan.

External references keep their explicit stable source id.

The runtime exposes separate routing for:

```text
source property change
component property change
component event
```

Component-property routing allows a host to propagate derived Property changes through the reverse index without rescanning the whole DSL program.

## Trigger vs read dependencies

The M6.5.6 distinction is preserved during execution.

Example:

```text
if device.fault {
  component.showFault(device.pressure)
}
```

`device.fault` is a trigger dependency. `device.pressure` is only a read dependency used when the Action actually fires.

Changing pressure alone therefore does **not** wake or replay the Behavior.

Likewise, Interaction Action arguments are read only when the matching Component Event occurs.

## Pure runtime effects

`evaluateScadaDslRuntimeTargets()` evaluates only the selected Value/Behavior plans and returns structured effects:

```text
Property updates
Component Action effects
next active Behavior branch state
diagnostics
```

It performs no external side effect itself.

Behavior keeps branch-entry semantics from M6.5.5:

```text
same active branch -> no replay
new active branch  -> fire that branch once
```

`evaluateScadaDslComponentEvent()` resolves only the matching Interaction(s) and prepares concrete Device Action effects. The host remains responsible for dispatching those effects.

This preserves the boundary:

```text
DSL/runtime core -> describe/evaluate effects
host             -> execute effects
```

and avoids recreating an imperative script engine inside SCADA.

## Verification

Covered by `scripts/check-scada-dsl-runtime.ts` and CI runtime-model checks.

The acceptance test proves:

- only affected Value Binding / Behavior plans are routed for a source update;
- read-only Action arguments do not become triggers;
- external source references remain stable;
- Component Property dependencies are reverse-indexed;
- repeated telemetry in the same Behavior branch does not replay a one-shot Component Action;
- Component Events look up only matching Interaction plans;
- Interaction Action arguments are read at event time;
- primary-device rebinding changes runtime context without recompiling the DSL.

## Deferred

Not part of M6.5.7:

- automatic propagation loop/session that applies Property updates and recursively routes derived Component Property changes;
- cycle detection for component-property dependency graphs;
- host wiring to Preview Runtime;
- Action parameter schema/type validation;
- persistence/schema migration;
- DSL editor UI/LSP surface;
- QuickJS adapter.

The next runtime slice should decide the minimal host-owned session/propagation contract and add cycle protection before integrating this path into Preview Runtime.
