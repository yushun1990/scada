# M6.7B2A Remote component repository + install boundary

Status: accepted implementation gate · 2026-08-29

## Goal

Establish the browser-side read boundary for the immutable publication API without turning remote discovery into automatic runtime activation or introducing browser write credentials.

## Accepted boundary

```text
Remote Publication API
        ↓ public read
RemoteComponentRepository
        ↓ strict publication-contract parsing
PublishedComponentRevision
        ↓ explicit conversion
RemoteComponentInstallCandidate
        ↓ future install/cache decision
local activation path
```

There is deliberately no direct edge from the remote HTTP repository to `studioComponentRegistry`.

## RemoteComponentRepository

The browser-facing interface supports:

- publication-head listing
- latest revision lookup by component type
- specific immutable revision lookup

The HTTP implementation:

- performs no I/O merely by being constructed
- issues credential-free public GET requests
- encodes a component type as one URL path segment
- treats 404 as a normal missing latest/revision result
- surfaces other HTTP failures as explicit repository errors carrying HTTP status and server error code when available
- parses every successful response through the accepted M6.7B1 publication contract
- fails closed when a 200 response contains malformed publication metadata/package content

No `SCADA_ADMIN_TOKEN` or other publication credential is invented or attached to public reads.

## Why remote catalog does not auto-activate

A developer may have:

```text
local authored package:    custom.pump
published remote revision: custom.pump
```

Those are two origins of the same component type, not two independent component types.

Blindly concatenating the remote latest set with local ready packages and sending both to the M6.7A activation controller would create a false type collision and disable both.

Therefore remote discovery remains catalog state until an explicit install/cache policy chooses which remote revision is locally installed and how it interacts with a local authored package.

## Provenance-preserving install candidate

`createRemoteComponentInstallCandidate()` converts a validated immutable revision into:

```text
source
  kind = remote-publication
  componentType
  revision
  revisionId
  publishedAt

entry
  synthetic ready ComponentLibraryEntry
```

Provenance is kept beside the ComponentLibraryEntry rather than stuffed into local authoring fields such as `id`, `status`, or `updatedAt` and mistaken for authoring identity.

Before a future install/cache step can use the synthetic entry, it is run through the accepted local component serializer/validator again.

The conversion itself performs no persistence and no runtime activation.

## Verification

`scripts/check-remote-component-repository.ts` verifies:

- construction performs no remote request
- public reads carry no Authorization header
- base URL normalization
- component-type URL encoding
- valid list/latest/specific-revision parsing
- 404 -> null semantics
- invalid revision arguments are rejected before I/O
- malformed successful responses fail closed
- explicit HTTP/server error propagation
- remote revision -> provenance-preserving install candidate conversion
- candidate revalidation through the local package codec

The first fixture version intentionally used an obsolete hand-written visual schema and was rejected by the production parser; the fixture was corrected to use the canonical visual factory rather than weakening validation.

CI #678 passed Build, all Runtime model checks including this remote-repository fixture, Lint, and the independent PostgreSQL publication-api job.

## Non-goals

B2A does not include:

- startup-time remote fetch
- automatic remote activation
- IndexedDB remote package cache
- offline installed-package persistence
- remote/local conflict resolution UI
- browser publish operation
- browser authentication
- production deployment

## Next gate

M6.7B2B should implement **explicit install + offline cache** with durable remote provenance.

The storage design must make an installed immutable remote revision distinguishable from an editable local authored package. Installing a remote artifact must not silently convert it into an ordinary authoring draft, and remote unavailability must not break a previously installed component required by a local Scene.
