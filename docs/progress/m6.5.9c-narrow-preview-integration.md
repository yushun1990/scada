# M6.5.9C Narrow Preview integration

Status: implementation complete · review gate

Date: 2026-08-28

## Goal

Connect the accepted compiled SCADA runtime to real Preview runtime state through the M6.5.9B ownership model without expanding Scene persistence or inventing the M6.5.10 typed Action/Event contract early.

The accepted runtime flow is now:

```text
RuntimeValueStore publication
        ↓
tracked compiled source dependency diff
        ↓
transactional propagation session
        ↓
ComponentPropertyStore derived commit
        ↓ settled effective snapshot
        ├─ Renderer
        └─ Component Action handler

Component Event
        ↓
compiled Interaction Binding
        ↓
Device / Platform Action effect
        ↓
narrow host dispatcher callback
```

## Delivered integration boundary

`attachPreviewScadaSemantics()` attaches one already-validated `ScadaDslCompiledRuntime` to one live Preview component node.

It does not compile source text, mutate Scene v6, or persist DSL state. The adapter owns only runtime attachment lifecycle and host sequencing.

The bridge:

1. claims compiled semantics for the component node
2. creates one transactional propagation session
3. reads external source values from `RuntimeValueStore`
4. reads component base properties from `ComponentPropertyStore`
5. initializes the full compiled program
6. commits settled derived property effects into Preview state
7. executes Component Action effects only after the settled commit
8. routes Component Events through compiled Interaction Bindings
9. forwards Device / Platform Action effects to a host callback
10. releases derived state and the compiled claim on disposal

## Component Property base vs effective state

M6.5.9B established one effective Preview Component Property owner. M6.5.9C makes its lower boundary explicit.

`ComponentPropertyStore` now owns two related immutable snapshots:

```text
base snapshot
= component defaults
  + authored Scene props
  + legacy Scene v6 runtime-value binding layer

final effective snapshot
= base snapshot
  + compiled DSL derived override layer
```

The propagation session reads only the base snapshot when a derived property has no current DSL override.

This is important: reading the final effective snapshot as the session's host base would feed the previous derived value back into the next propagation transaction and make invalidation/rebind semantics dependent on stale runtime state.

Renderer and Component Action handlers continue to consume only the final effective snapshot.

## Source publication batching

`RuntimeValueStore.setMany()` publishes one immutable source snapshot. M6.5.9C preserves that publication boundary.

The propagation session now supports:

```text
sourcePropertiesChanged([...changes])
```

All changed source properties relevant to the compiled reverse index are unioned and ordered by the authored semantic plan before one propagation transaction begins.

Therefore a multi-property source publication cannot cause Behavior evaluation against an intermediate state such as:

```text
new pressure + old running state
```

when both properties arrived in the same host publication.

This extends the existing propagation transaction boundary from one source property to one source publication.

## Source dependency filtering

The Preview bridge does not replay the compiled program for every external scalar update.

It tracks only references that can trigger the attached compiled program:

- current Primary Device properties present in `primarySourceTriggers`
- explicit external source/property pairs present in `externalSourceTriggers`

For each RuntimeValueStore publication it compares the previous/current value and presence state for those tracked references. Deletion is treated as a source change so unresolved Value Bindings can release their derived override.

The default host key convention is:

```text
<sourceId>:<property>
```

A host may provide a different `sourceValueKey` mapping without changing the compiled DSL runtime.

## Settled Component Action semantics

Propagation remains side-effect free until it returns a successful transaction result.

Preview applies a successful result in this order:

```text
1. report runtime diagnostics
2. commit all derived Component Property ownership/value updates
3. publish the new final Component Property snapshot
4. execute returned Component Action effects
```

Because `PreviewRuntime.invokeAction()` reads from the same `ComponentPropertyStore` used by Renderer subscriptions, a Component Action observes the exact immutable object representing the already-settled rendered state.

No partial Property update is exposed before downstream Value Bindings settle.

## Interaction handoff and legacy compatibility

The bridge uses M6.5.9B's compiled-semantics claim for its node.

While attached:

- Component Events are still published by Preview
- legacy Scene v6 Event -> Component Action auto-dispatch is suppressed for that node
- the compiled propagation session receives the Component Event
- matching Interaction Bindings produce Device / Platform Action effects
- each effect is forwarded once to the host dispatcher callback

After disposal the claim is released and compatibility-only Scene v6 behavior may run again.

This prevents the old and new event models from firing in parallel during the transition period.

## Action/Event typing boundary

M6.5.9C deliberately does not invent the final Action/Event input contract.

The current public component handler accepts one `unknown` input while DSL Action calls already model positional scalar arguments. Guessing a mapping here would prematurely freeze M6.5.10 design.

Therefore:

- zero-argument Component Actions execute through Preview now
- parameterized Component Action effects are diagnosed and not dispatched by this bridge
- Device / Platform Action effects are forwarded as the existing structured runtime effect
- M6.5.10 owns Action parameter schema, Event payload schema, handler input shape, static validation and the production device-action dispatch interface

## Primary-device rebind

The Preview attachment delegates rebind to the M6.5.9A transactional propagation session.

Successful rebind:

1. derives against a fresh override map
2. commits only the final old/new derived delta into ComponentPropertyStore
3. changes the attachment's Primary Device atomically
4. preserves explicit external source references

If the new Primary Device lacks required source data, old-device derived values are explicitly released and the effective Preview property falls through to its base snapshot.

Old-device values therefore cannot leak into the rebound component.

## Abort semantics

A propagation-step-limit abort remains a full host boundary.

For both source-publication propagation and Primary Device rebind:

- staged session derived values are discarded
- staged Behavior branch state is discarded
- `valueUpdates` is empty
- `componentActions` is empty
- Preview does not commit a new derived snapshot
- the previously committed Component Property snapshot remains intact
- an aborted rebind also restores the previous Primary Device

The regression fixture asserts object identity for the previously committed Preview snapshot, not only value equality, to prove that no host publication escaped the aborted transaction.

## Regression fixture

`scripts/check-preview-scada-integration.ts` proves the end-to-end narrow flow with a renderer-independent test component.

Coverage includes:

- initial source value -> compiled Value Binding -> rendered Component Property
- downstream derived property settling before Behavior evaluation
- Component Action handler receiving the exact Renderer snapshot object
- source updates leaving authored Scene props unchanged
- Component Event -> exactly one Interaction device action effect
- suppression of parallel legacy Scene v6 Event behavior while compiled semantics owns the node
- Primary Device rebind with missing new-device data releasing old derived values
- subsequent new-device source updates and interaction resolution
- attachment disposal releasing derived state and restoring legacy compatibility behavior
- one `setMany()` publication feeding one source propagation transaction
- forced source-batch propagation abort exposing no partial Preview effect
- forced Primary Device rebind abort preserving previous primary + exact Preview snapshot

The fixture is wired into CI after the existing M6.5.9B Preview state checks.

## Scope boundary

This slice intentionally does not add:

- a Scene schema revision
- persisted DSL source or semantic plans
- Workbench UI for selecting/storing compiled semantics
- broad scene-wide semantics orchestration
- typed Action parameter schemas
- typed Event payload schemas
- a production Device / Platform Action transport
- backend deployment or persistence
- QuickJS/general-purpose scripting work

Those remain outside M6.5.9C.
