# M6.5.6 SCADA DSL Static Analysis

Status: **accepted as a non-UI semantic checkpoint**.

This slice adds compile-time analysis on top of the already accepted text-first DSL surface and semantic lowering. It does not change Scene persistence and does not introduce an editor UI.

---

## 1. Scope

Implementation:

- `src/scene/scada-dsl-analysis.ts`
- `scripts/check-scada-dsl-analysis.ts`

The slice adds two capabilities:

1. static scalar type checking before runtime execution;
2. dependency extraction for later incremental reevaluation/subscription planning.

---

## 2. Static type model

The first type system is intentionally small:

```text
number
boolean
string
null
```

Component/source Property definitions map into these scalar families. `select` Properties derive their scalar family from options/defaults rather than receiving implicit coercion rules.

The DSL does **not** perform implicit conversions such as:

```text
"1" -> 1
1 -> true
```

Operator rules are deliberately strict:

```text
and / or / not       -> boolean only
+ - * / %            -> number only
> >= < <=            -> number only
== !=                -> compatible scalar families
if condition         -> boolean only
```

Value Binding assignment must be compatible with the target Component Property.

Examples rejected before runtime:

```text
component.level = device.running
```

```text
if device.pressure {
  component.pulse()
}
```

```text
component.level = device.running + 1
```

Action argument schemas are intentionally **not** checked yet because the current Component Action contract does not define parameter schemas. Expressions used as Action arguments are still checked internally for operator/type correctness.

---

## 3. Dependency index

Semantic plans can now be converted into a dependency index.

Dependencies retain structured references:

```text
component Property
primary-device Property
explicit external source Property
```

Primary-device dependencies remain relative:

```text
{ scope: "primary-device", property: "pressure" }
```

They do not capture the concrete device selected while authoring, preserving copy/rebind behavior.

The index distinguishes two dependency classes.

### Trigger dependencies

A change to these dependencies may require recomputation or branch selection.

For a Value Binding:

```text
component.level = outlet.pressure * 100
```

`outlet.pressure` is a trigger dependency.

For a Behavior:

```text
if device.fault {
  component.pulse(device.pressure)
}
```

`device.fault` is a trigger dependency.

### Read dependencies

These values must be available when a binding/action executes, but changing them alone must not cause a one-shot Behavior Action to replay.

In the previous example:

```text
device.pressure
```

is a read dependency of the Action argument but **not** a trigger dependency.

This preserves the accepted branch-entry behavior semantics:

```text
condition remains in same active branch
+ Action argument value changes
=
no repeated Component Action
```

For Interaction Binding:

```text
on component.startRequested {
  device.start(outlet.pressure)
}
```

there is no data trigger dependency. The Component Event is the trigger; `outlet.pressure` is only a read dependency evaluated at interaction time.

---

## 4. Why this matters

The runtime no longer needs to treat every telemetry update as a reason to scan every DSL behavior.

The intended later execution model can be:

```text
point update
   ↓
dependency lookup
   ↓
only affected Value Bindings / Behavior conditions
   ↓
reevaluate
```

while Action-only parameter dependencies remain subscribed/readable without becoming behavior triggers.

This is especially important for SCADA pages with many components and frequent telemetry.

---

## 5. Boundaries retained

This slice does not change the previously accepted architecture:

- DSL remains an authoring/interaction surface, not the persistence model;
- Value Binding remains declarative;
- Behavior `if / else if / else` keeps ordered branch-entry semantics;
- data-driven Device Actions remain rejected;
- Device Actions are reached through explicit Component Event Interaction;
- Component Action parameter schemas remain deferred;
- Scene schema is unchanged;
- no UI editor is added.

## 7. Next checkpoint

The next useful step is to introduce a small **compiled binding plan/runtime index** that consumes the dependency index and proves incremental scheduling without changing Scene persistence.

It should demonstrate:

```text
source Property update
  -> find affected Value Binding / Behavior only

Component Event
  -> find matching Interaction only
```

and preserve:

```text
same Behavior branch
  -> no Action replay
```

Do not add the production DSL editor UI until this runtime scheduling boundary is proven.
