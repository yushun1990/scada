# M6.3.3 Property-driven Visual Rules

Status: implemented on `main` · CI #405 ✅ · manual browser smoke pending.

This slice connects the public Component Property contract to the private visual implementation without exposing Konva or introducing user scripts.

## Goal

Provide a small declarative rule layer for common SCADA state-driven visuals:

```text
Component Property value
        ↓
Visual Rule condition
        ↓
private Layer target
        ↓
resolved ComponentVisualDefinition
        ↓
Composite Renderer
```

Examples:

```text
state == running
  -> pump-body.style.fill = #22c55e

alarm == true
  -> alarm-light.visible = true

pressure >= 10
  -> warning-text.style.fill = #ef4444
```

Rules are deliberately not an expression language. Numeric formulas such as `level / 100` remain a later Expression capability.

## Rule model

A Visual Rule is serialized private component implementation data:

```text
id
enabled
propertyKey
operator
compareValue
layerId
target
value
```

Supported condition operators:

```text
equals
notEquals
greaterThan
greaterOrEqual
lessThan
lessOrEqual
```

Relational operators are valid only for number Properties.

Rules are evaluated in serialized order. If multiple matching rules write the same visual target, the later rule wins.

## Typed target surface

All Layers can target:

```text
visible
opacity
transform.x
transform.y
transform.width
transform.height
transform.rotation
transform.scaleX
transform.scaleY
```

Vector Layers additionally expose:

```text
style.fill
style.stroke
style.strokeWidth
```

Text Layers additionally expose:

```text
style.fill
style.fontFamily
style.fontSize
style.fontStyle
style.align
style.verticalAlign
style.lineHeight
```

SVG/Image Layers additionally expose:

```text
style.fit
```

The rule model therefore targets the renderer-independent typed visual surface established in M6.3.2 rather than raw Konva nodes.

## Evaluation boundary

`resolveComponentVisualRules()` is a pure resolution step. It does not mutate the authored package and does not write editor history.

```text
Authored ComponentVisualDefinition
          +
resolved ComponentProps
          ↓
resolveComponentVisualRules()
          ↓
resolved visual snapshot
          ↓
renderer
```

The Component Workbench applies rules in Preview mode only. Design mode continues to edit the authored base visual, preventing rule-driven transforms from fighting the Transformer interaction.

## Workbench authoring

- Selecting a private Layer exposes a `视觉规则` group below the Layer Style controls.
- Rules for that Layer can select a public Property, condition operator, typed comparison value, visual target and typed target value.
- Rule value editors follow the Property/target type: boolean checkbox, number input, enum select or text/color value.
- Rules can be enabled/disabled or deleted.
- A Layer with no Component Properties explains that the public Property contract must be defined first.

## Preview values

Preview mode now owns temporary Component Property values.

- Select the component root in Preview to edit `预览数据`.
- Preview values initialize from public Property defaults.
- Preview values are not written back to `ComponentDefinition.defaultValue`.
- Preview values are not persisted into the Component Package.
- Changing a preview value immediately re-resolves Visual Rules and rerenders the component.

## Referential integrity

Rules are validated against both public and private component contracts before package save/load acceptance.

Validation rejects:

- missing Property keys;
- comparison values incompatible with the Property type;
- numeric comparison operators used on non-number Properties;
- missing Layer IDs;
- targets unsupported by the target Layer kind;
- invalid target value types/ranges.

Workbench edits also preserve rule references:

- renaming a public Property rewrites matching rule `propertyKey` references;
- deleting a public Property removes its rules;
- changing a Property kind/options resets an incompatible comparison to the new default and returns to equality when necessary;
- renaming a Layer rewrites matching rule `layerId` references;
- deleting a Layer/Group removes rules targeting deleted Layers.

## Compatibility

`ComponentVisualDefinition` remains schema version 2.

`rules` is optional for previously saved v2 visuals, so existing components remain valid without migration. Cloning normalizes missing rules to an empty rule list.

## Boundaries

Not included in this slice:

- general expression syntax / formulas;
- Property-to-Property assignments;
- text-content binding expressions;
- animation start/stop targets;
- controlled scripts;
- Runtime/SCADA publication of Workbench-authored components;
- asset library/upload persistence;
- 2.5D projection.

## Manual browser smoke

Recommended smoke path:

1. Create a `select` Property named `state` with values `stopped` and `running`.
2. Select a Vector Layer and add a Visual Rule: `state == running -> style.fill = #22c55e`.
3. Add another rule: `state == stopped -> style.fill = #94a3b8`.
4. Switch to Preview, select the component root, and change `state` in `预览数据`; confirm the Layer color switches immediately.
5. Test a boolean Property driving `visible`.
6. Test a number Property with `greaterThan` driving Text color or opacity.
7. Save/reopen and confirm rules persist.
8. Rename the Property and Layer and confirm rules remain attached.
9. Delete a target Layer/Group and confirm its rules are removed rather than blocking save.
10. Return to Design and confirm the base visual remains editable and is not rewritten by preview rule results.
