# M6.5.4 SCADA DSL Surface

Status: **first text-first interaction slice accepted as an exploratory UI surface; runtime/serialization semantics are not frozen**.

This slice follows the Component Behavior review and deliberately separates two concerns:

```text
what the user edits
    !=
what the runtime persists/executes
```

The DSL introduced here is a **SCADA Workbench interaction surface**. It does not replace the structured Value / Behavior / Interaction Binding model and is not a general scripting runtime.

---

## 1. Product intent

The normal scene author should be able to express UI dynamics with a very small language while the editor supplies all component/device capabilities through discovery UI.

The intended authoring experience is:

```text
small DSL editor
+ LSP-like completion
+ clickable capability tags
+ device/component capability browser
```

The user should not have to memorize a component's Properties/Actions or a device's points/actions.

Examples of the intended surface:

```text
component.level = device.pressure
```

```text
component.state = if device.fault then "fault" else "normal"
```

```text
if device.fault and device.pressure > 1.2 {
  component.showFault()
} else if device.running {
  component.showRunning()
} else {
  component.showStopped()
}
```

The exact formatting/keywords remain revisable before an editor UI is built.

## 2. Implemented surface contract

Implementation:

- `src/scene/scada-dsl.ts`
- `scripts/check-scada-dsl.ts`

The first parser/AST slice supports:

- Property references such as `component.state` and `device.pressure`;
- arbitrary editor-provided source symbols such as `outlet.pressure`;
- scalar literals;
- arithmetic operators `+ - * / %`;
- comparison operators `== != > >= < <=`;
- boolean `and / or / not`;
- direct Property assignment;
- expression-style `if ... then ... else ...`;
- statement-style `if / else if / else` blocks;
- Action calls with expression arguments;
- comments;
- parser diagnostics with source spans.

This is intentionally **not** JavaScript and does not currently include:

```text
let / mutable variables
user-defined functions
for / while loops
timers / sleep
async / await
network access
DOM/browser access
arbitrary object mutation
```

## 3. Capability discovery contract

The same module also introduces a renderer/UI-independent capability catalog for future editor assistance.

A catalog item records:

```text
source stable id
source title
editor symbol
member name
Property / Action / Event kind
display title
component capability metadata where available
```

Examples:

```text
component.showFault

device.pressure

outlet.pressure
```

The catalog is designed to feed both interaction paths:

### Keyboard-first

Typing:

```text
component.sh
```

can produce completion candidates such as:

```text
showFault()
showRunning()
showStopped()
```

### Mouse-first

A visible capability tag can use the same catalog item and insert its full text at the current cursor position:

```text
[ Pressure ]
    ↓ click
outlet.pressure
```

Therefore completion and clickable tags are two presentations of one capability-discovery source rather than separate feature models.

## 4. Important architectural boundary

This DSL is **not** the source of truth for device/component identity.

The long-term editor/compiler must resolve readable symbols against structured stable references before persistence/runtime execution.

For example:

```text
device.pressure
```

may resolve to:

```text
primary-device context
+ Property capability "pressure"
```

while:

```text
outlet.pressure
```

may resolve to a stable explicit external-device reference selected by the authoring UI.

Renaming a display label or copying/rebinding a component must not depend on fragile string replacement.

The previously accepted primary-device direction remains:

```text
copy configured component
    ↓
change primary device
    ↓
relative `device.*` references resolve against the new device
```

---

## 5. What is intentionally not settled yet

The parser proves that the desired interaction vocabulary can remain small and readable. It does **not** yet freeze behavior execution semantics.

Before compiling DSL into scene/runtime bindings, the next pass must settle:

1. what an Action inside an `if` branch means when telemetry is re-evaluated repeatedly;
2. whether branch Actions fire only when a branch becomes active, and how `else` transitions behave;
3. how direct assignment maps to Value Binding and type validation;
4. how Component Action parameters are typed once Action definitions gain parameter schemas;
5. how Component Events / user interactions are represented in the text surface;
6. how readable editor symbols map to stable primary/external device references;
7. error recovery for partially typed text so completion remains useful while the source is temporarily invalid;
8. whether the final visual syntax uses braces, indentation, or another equally small presentation.

Do not build the production editor around the current punctuation before these semantics are reconciled.

## 7. Next checkpoint

The next useful slice is **DSL semantic lowering**, not a code editor UI.

It should prove that a small set of DSL forms can lower deterministically into the already separated runtime concepts without making the text language the persistence model:

```text
Property assignment
    → Value Binding / derived value

conditional Component Action
    → Behavior Binding / transition semantics

Component Event → Device Action
    → Interaction Binding
```

Only after this lowering/semantic boundary is stable should the SCADA Workbench editor UI be implemented with completion and clickable capability tags.
