# M6.7A Local user-component activation

Status: accepted implementation gate · 2026-08-29

## Goal

Prove that a Component Workbench-authored package stored in the accepted local ComponentRepository can enter SCADA through the same generic ComponentRegistry-facing runtime path as built-ins, without introducing a backend or executing persisted implementation text.

## Accepted runtime path

```text
Component Workbench
        ↓ save
IndexedDB ComponentRepository
        ↓ hydrate / parse package
user-component activation controller
        ↓ validate eligibility + collisions
ComponentRegistration
        ↓
product-wide studioComponentRegistry
        ├─ SCADA palette
        ├─ Scene validation
        ├─ anchors / connection semantics
        ├─ renderer
        ├─ inspector contract lookups
        └─ PreviewRuntime
```

The critical result is that package origin is no longer part of the SCADA runtime contract. Built-ins and locally authored packages meet at ComponentRegistration / ComponentRegistry.

## Shared live registry

`studioComponentRegistry` is now the product-wide live registry. Built-in registrations form its fixed baseline. The previous `builtInComponentRegistry` export remains temporarily as an object-identity compatibility alias, so existing consumers continue to resolve the same live registry while call sites are migrated deliberately rather than by a broad rename.

`ComponentRegistry.unregister()` provides the narrow lifecycle primitive required to replace the user-owned portion deterministically.

## Declarative composite registration

`createCompositeComponentRegistration()` converts an already-validated declarative component definition + composite visual into a normal ComponentRegistration.

The generated runtime renderer reuses the existing generic component machinery:

- Component Property defaults and effective props
- composite layer rendering
- Property-driven visual rules
- generic visual animation evaluation / overlay
- standard Scene transform, drag, resize and rotation contract

No component-specific SCADA renderer code is generated.

Most importantly, `implementationDraft` is not read or evaluated by activation. Persisted source text does not become executable merely because a package reaches `ready` status.

## Activation eligibility

M6.7A intentionally accepts only the subset whose implementation is already fully declarative:

- package is user-authored (`builtIn === false`)
- status is `ready`
- visual mode is `composite`
- public Action map is empty
- public Event map is empty
- type does not collide with a built-in
- type is unique among all ready user packages in the replacement set
- the resulting ComponentRegistration passes normal registry validation

The following are diagnosed and skipped rather than partially activated:

- draft packages
- native user visuals requiring a trusted native renderer
- packages declaring Actions or Events without an accepted executable implementation contract
- built-in type collisions
- duplicate ready user types
- invalid registration construction

No arbitrary winner is selected for duplicate types, and no fake/no-op Action or Event implementation is installed.

## Transactional replacement semantics

Activation rebuilds the complete next user-registration set before mutating the live registry.

```text
repository snapshot
        ↓
build + validate complete candidate registration set
        ↓ success
remove previous user registrations
        ↓
install complete new user set
```

This gives deterministic behavior for:

- `ready → draft`
- component type rename
- package deletion
- repository rehydrate
- debug snapshot import followed by hydration

Old user registrations do not remain live after repository state changes. Built-in registrations are never removed by the user activation controller.

## Scene hydration ordering

SCADA work listing/loading hydrates user component registrations before parsing stored Scene documents.

This ordering is required because Scene v7 validates component type, Properties, Actions, Events and persisted SCADA semantics against the current component contract. A Scene containing a valid local user component must not be rejected merely because Scene parsing raced ahead of ComponentRepository hydration.

## Deterministic verification

`scripts/check-user-component-activation.ts` exercises the activation core without loading browser-only built-in assets. It verifies:

- ready declarative composite activation
- draft exclusion
- native user visual exclusion
- Action/Event package exclusion until an executable implementation contract exists
- built-in collision rejection
- duplicate ready user type rejection for every colliding package
- invalid package isolation
- stale user-registration removal on replacement
- `ready → draft` deactivation
- preservation of the built-in baseline

The fixture is part of the normal CI Runtime model checks.

CI #666 on PR #88 passed Build, Runtime model checks and Lint with this fixture enabled.

## Accepted boundary

M6.7A does not include:

- remote publication
- authentication
- backend provisioning
- package revision APIs
- synchronization
- marketplace/discovery
- arbitrary JavaScript execution
- execution of `implementationDraft`
- a trusted native-renderer upload mechanism
- a user Action/Event implementation runtime

Those are separate concerns and must not be smuggled into local activation.

## Next gate

> Local and remote packages must converge into the same validated package → ComponentRegistration → ComponentRegistry runtime path. The backend is a package distribution/persistence concern, not SCADA runtime authority.
