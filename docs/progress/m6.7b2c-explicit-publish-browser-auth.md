# M6.7B2C Explicit publish + browser-safe authentication

Status: accepted implementation gate · 2026-08-29

## Goal

Connect Component Workbench to the immutable publication API without making local Save a remote write, leaking server credentials into the frontend, or weakening the accepted `baseRevision` optimistic-concurrency contract.

## Accepted browser publication path

```text
local ready ComponentLibraryEntry
        ↓ explicit Publish (separate from Save)
persisted last-observed remote revision
        ↓ baseRevision
HttpComponentPublicationClient
        ↓ credentials: include · no admin-token option
opaque HttpOnly publication session
        ↓ server-side session hash + publisher identity
immutable publication transaction
        ↓
PublishedComponentRevision
        ↓ successful publish only
advance local publication observation
```

`VITE_PUBLICATION_API_URL` is public routing configuration only. It is not a credential.

## Save and Publish remain different operations

Component Workbench keeps two independent actions:

- **Save** persists the local authoring package through the existing IndexedDB component repository.
- **Publish** sends the current validated `ready` package through the publication client.

Publish does not silently call Save, and Save does not silently publish.

Built-in packages and local packages that are not `ready` are not publishable from the browser UI.

## Last-observed revision is publication state, not authoring state

The browser stores a separate `ComponentPublicationObservation` keyed by component type:

```text
componentType
revision | null
revisionId | null
observedAt
```

It lives in the browser persistence metadata boundary rather than inside `ComponentLibraryEntry`.

Accepted rules:

- when no observation exists, the first explicit Publish performs one explicit latest-revision observation and persists it
- a publish request uses that persisted revision as `baseRevision`
- a successful publish advances the observation to the returned immutable revision
- later publishes reuse the persisted observation and do **not** secretly fetch latest first
- `409 publication_conflict` is surfaced to the user with the server's current revision
- conflict does not mutate the stored observation and does not auto-retry
- the user must explicitly choose **Refresh remote state** before a later publish can adopt a newer remote base

This preserves the concurrency meaning accepted in M6.7B1 instead of turning `baseRevision` into a decorative field.

## Browser authentication boundary

The public frontend never receives `SCADA_ADMIN_TOKEN`.

The accepted browser flow is:

```text
username + password
        ↓ HTTPS login request from an allowed browser Origin
server verifies configured publisher identity
        ↓
random opaque session id
        ├─ browser: HttpOnly cookie
        └─ PostgreSQL: SHA-256 session hash + identity + expiry
```

The current implementation intentionally provides a narrow self-hosted single-publisher identity source through server configuration:

- `SCADA_PUBLISH_USERNAME`
- `SCADA_PUBLISH_PASSWORD`

This is sufficient to establish the browser/session/identity contract for the current gate. It is not a claim that environment-backed single-user credentials are the final multi-user IAM design.

Important security properties:

- the browser publication client exposes no bearer-token/admin-token parameter
- the session cookie is opaque and HttpOnly
- only the session hash is stored in PostgreSQL
- sessions have an explicit TTL
- logout deletes the server-side session and expires the cookie
- publication rows record `published_by` identity
- request-id replay is accepted only for the same publication input **and the same publisher identity**
- browser login/logout/session-authenticated Publish require an Origin from the configured allowlist
- CORS credentials are enabled only for configured origins
- the server/CI administrator Bearer remains a separate non-browser operations channel

Production defaults use a Secure cookie. Local CI intentionally overrides Secure/SameSite settings for loopback HTTP integration testing.

## Cross-site deployment note

The current browser contract supports credentialed cross-origin requests, but production topology must not assume third-party-cookie availability forever.

Before deployment, prefer a same-site/custom-domain topology for frontend + API when practical, or explicitly verify the chosen browser/cookie behavior. This is one reason production infrastructure remains a review gate rather than being provisioned automatically by B2C.

## Client / adapter separation

The publication transport and publication-observation state machine are browser-independent.

```text
HttpComponentPublicationClient
ComponentPublicationObservationStore
        ↓
        ├─ Memory fixture implementation
        └─ browser IndexedDB-meta adapter (loaded only when needed)
```

An early fixture exposed that statically importing browser persistence pulled renderer assets into a Node-only test. The implementation was corrected by splitting the browser adapter from the pure client boundary rather than weakening the fixture.

## Workbench UX

Component Editor now provides:

- a dedicated **Publish** control separate from **Save**
- session login/logout state
- explicit publisher identity display
- current persisted remote observation
- explicit **Refresh remote state**
- clear conflict messaging explaining local `baseRevision` versus server current revision
- no silent overwrite and no automatic conflict retry

Remote publication remains optional. If `VITE_PUBLICATION_API_URL` is not configured, local editing and Save continue normally.

## Verification

Deterministic client checks cover:

- browser transport always using cookie credentials
- no Authorization header emitted by the browser publication client
- explicit conflict code/current-revision propagation
- first observation and `baseRevision` selection
- successful observation advancement
- repeated publish without hidden latest reads
- conflict leaving the observation unchanged
- explicit refresh as the only path that adopts a newer remote head

The real PostgreSQL 16 integration job covers:

- anonymous public reads
- browser-auth configuration health state
- blocked untrusted Origin
- invalid login
- opaque HttpOnly session creation with explicit identity
- unauthenticated write rejection
- session-authenticated revision creation
- request idempotency and publisher-bound replay
- stale `baseRevision` conflict
- immutable historical revision retrieval
- session revocation on logout
- separate administrator Bearer publication

Final implementation head `708003dfae9cce744a477bfe8c72513d5340e213` passed CI #691: Build, all Runtime model checks including the new browser publication fixture, Lint, and the independent PostgreSQL publication-api integration job.

## Non-goals

M6.7B2C does not include:

- production backend provisioning
- production DNS/TLS/CORS configuration
- external OIDC/SSO integration
- multi-user roles or ACLs
- password reset/account management
- marketplace/catalog UX
- automatic publication on Save
- automatic conflict resolution
- automatic remote catalog activation

## Next gate

B2C removes the architectural blocker on considering production infrastructure; it does **not** mean production deployment should begin without review.

The next step should be a focused production deployment/topology decision covering API URL/domain layout, cookie/site behavior, production identity choice, credential rotation/secrets, PostgreSQL migration/backup, TLS/CORS and end-to-end browser smoke requirements. The result may be either **deploy now** or **defer deployment** before M7 product packaging work proceeds.
