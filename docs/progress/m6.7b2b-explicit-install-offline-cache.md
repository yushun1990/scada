# M6.7B2B Explicit install + offline cache

Status: accepted implementation gate · 2026-08-29

## Goal

Allow one validated immutable remote component revision to be explicitly installed into durable browser-local storage, remain usable while the remote publication service is unavailable, and activate through the already-accepted M6.7A user-component activation path without being confused with an editable local authored package.

## Accepted storage boundary

```text
RemoteComponentInstallCandidate
        ↓ explicit install
InstalledRemoteComponent
  source: immutable remote provenance
  entry: validated ready package
  installedAt: local install timestamp
        ↓ dedicated repository
IndexedDB installedRemoteComponents (schema v2)
        ↓ startup hydration, no remote fetch
M6.7A user-component activation controller
        ↓
studioComponentRegistry
        ↓
Scene validation / editor / preview
```

Installed remote artifacts are not written into the ordinary editable `components` store.

## Durable provenance

Each installed artifact stores the remote publication identity beside the package:

- `componentType`
- immutable `revision`
- immutable `revisionId`
- `publishedAt`
- local `installedAt`

The nested package remains a normal validated ready `ComponentLibraryEntry` for reuse by the M6.7A activation path, but its synthetic `published:<revisionId>` package identity and remote source metadata are checked together by the installed-artifact codec.

The codec fails closed if provenance and package identity disagree.

## Explicit install/update/uninstall semantics

The dedicated repository uses `componentType` as the cache slot key, so one component type has at most one installed remote revision.

Accepted semantics:

- installing a revision is an explicit operation; discovery never installs automatically
- reinstalling the exact same immutable revision/package is idempotent and preserves the original `installedAt`
- explicitly installing another revision replaces the installed cache slot for that component type
- replacement may move forward or backward, so an intentional rollback to an older immutable revision is supported
- uninstall removes only the installed remote cache entry
- published revisions themselves remain immutable; replacement changes which revision is locally selected, not the remote revision

## Local-authored vs installed-remote collision policy

Normal operations reject creation of a collision:

- a remote install is rejected when the component type is built in or already exists as an editable local authored package
- saving a local authored package is rejected when the same component type is currently installed from a remote publication

Historical/imported data can still contain both origins. Startup resolution is therefore deterministic:

> local authored wins; the installed remote artifact remains persisted but is not activated, and a type-collision diagnostic is emitted.

This policy avoids the earlier false behavior where blindly concatenating local and remote packages could make both lose activation through duplicate-type rejection.

## Offline startup and Scene validation

`prepareComponentLibrary()` now hydrates both:

- editable local authored component documents
- installed remote component documents

It resolves origin collisions, then sends the accepted package set to the existing M6.7A `replaceStudioUserComponentPackages()` activation path.

No remote repository is contacted during this startup path.

The existing SCADA work load order already calls `prepareComponentRuntimeRegistry()` before `parseSceneDocument()`. The legacy `builtInComponentRegistry` import used by Scene validation is an object-identity alias of `studioComponentRegistry`, so hydrated installed types are visible to Scene contract validation before a persisted Scene is parsed.

Remote service failure therefore cannot invalidate an already-installed component required by a local Scene.

## IndexedDB schema migration

Browser-local storage advances from schema v1 to v2.

The v2 upgrade is additive:

- existing `scenes` store remains intact
- existing editable `components` store remains intact
- existing `meta` store remains intact
- new `installedRemoteComponents` store is created with `id = componentType`

A deterministic migration fixture verifies that upgrading a v1-shaped database creates only the new installed-remote store.

## Debug snapshot reproducibility

Debug snapshot schema advances from v1 to v2 and now includes `installedRemoteComponents` because installed packages affect whether a Scene can be validated and reproduced offline.

Compatibility policy:

- v2 exports scenes, local components, and installed remote artifacts
- v2 browser import validates installed artifacts through the installed-artifact codec before the IndexedDB replacement transaction
- old v1 snapshots remain importable and migrate deterministically to an empty installed-remote slice

## Failure isolation

Installed cache hydration is fail-closed per row:

- malformed installed rows are not activated
- valid neighboring installed rows remain usable
- invalid row IDs are surfaced as activation diagnostics
- no startup remote fetch means transport/API outages do not touch the already-installed runtime state

## Verification

`scripts/check-remote-component-installation.ts` verifies:

- installed provenance/package codec round-trip
- provenance tamper rejection
- exact-revision reinstall idempotence
- explicit revision replacement
- intentional rollback to an older immutable revision
- one cache slot per component type
- local-repository-only hydration
- offline activation through the generic M6.7A activation controller
- deterministic local-authored-wins collision resolution
- corrupt installed-row isolation
- uninstall/idempotent missing-uninstall behavior
- additive IndexedDB v1 -> v2 schema migration

`scripts/check-storage-repositories.ts` additionally verifies:

- installed-remote Memory repository behavior
- debug snapshot v2 export/import/reset
- v1 debug snapshot compatibility

## Non-goals

M6.7B2B does not add:

- automatic remote catalog activation
- startup-time remote fetch
- editable conversion of an installed remote package
- automatic update to latest remote revision
- browser publication credentials
- explicit browser Publish UX
- production backend provisioning

## Next gate

M6.7B2C should implement **explicit publish + browser-safe authentication**.

Save and Publish must remain separate. The browser must never embed `SCADA_ADMIN_TOKEN`; publication should preserve the last observed remote revision for `baseRevision` and surface publication conflicts instead of silently overwriting or retrying.
